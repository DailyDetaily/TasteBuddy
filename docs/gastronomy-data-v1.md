# Taste Buddy 미식 데이터 — 전체 정보 구조 및 구현 설계

버전: 1.1 · 2026-09-15

최종 통합 대상: `feat/gastronomy-data-five-categories-20260915`, PR #2. 이전 `feat/experience-data-cards-20260915` 실험 구현은 함께 병합하지 않는다.

문서의 모든 음식명·수치·평가 사례는 **가상 예시**이며 실제 사용자 데이터가 아니다. 이 문서는 데이터 계약과 화면 설계다. 실제 빌드·실행 검증 여부는 해당 커밋의 CI 결과와 검증 기록을 구분해서 확인한다.

## 1. 확정한 정보 구조

홈은 경험 → 감각 → 취향 → 맥락 → 변화의 다섯 입구를 고정한다. 상세는 기간·집계 범위 → 카테고리 히어로 → 측정 카드 → 발견 카드 → 원본 기록으로 이어진다.

측정은 같은 정의로 계속 조회하는 데이터이며 특별한 차이가 없어도 유지한다. 발견은 여러 기록의 반복·공존·관계·대조·변화를 설명하며, 조건이 충족될 때 생성한다. 측정값을 문장으로 바꾼 것만으로 발견을 추가하지 않는다.

메뉴는 **식당별 개별 메뉴**, 음식 종류는 **별도 음식 분류**다. A식당 김치찌개와 B식당 김치찌개는 메뉴 2개다. 동일한 음식 분류가 확인되면 음식 종류는 김치찌개 1가지다. 넓은 ‘찌개’ 분류를 ‘김치찌개’로 바꾸지 않는다.

‘처음 기록한 경험’과 ‘다시 기록한 경험’은 각각 하나의 측정 카드이며 두 카드 모두 **메뉴 / 식당 / 음식 종류**를 전환한다. 같은 달에 처음 남긴 뒤 다시 기록한 메뉴는 두 카드 모두에 포함될 수 있다.

## 2. 공통 데이터 계약

### 정체성과 단위

`mealID`는 독립 식사, `DiningEntry.id`는 식사의 요리 기록이다. 한 끼의 여러 요리는 식사를 여러 번으로 만들지 않는다. 사진 추가·수정·재분석도 새 식사가 아니다. 같은 날짜를 근거로 서로 다른 mealID를 합치지 않는다.

동일 ID의 동일 원본은 중복 제거한다. 같은 ID에 충돌하는 원본이 있으면 해당 식사의 집계를 보류한다. 관련 요리 한 개만 빼고 나머지 요리를 확정된 식사처럼 세지 않는다.

식당은 확인한 지점 ID를 사용한다. 메뉴 ID를 우선하며, 확인된 식당 안에서는 직접 입력한 메뉴명을 그 식당 범위로 묶을 수 있다. 식당 이름만으로 지점 동일성이나 직접 만든 요리 여부를 확정하지 않는다. 음식 종류는 저장된 유효 분류 ID만 사용한다. 미확인 항목은 새로운 종류 하나로 만들지 않는다.

### 날짜

식사 경험의 기간 집계는 확인된 식사일을 사용한다. 저장일·촬영일 후보·수정일을 대신 넣지 않는다. 같은 식사의 날짜가 충돌하거나 일부만 확인됐다면 미확인으로 분리한다.

전체 누적에는 날짜 미확인 경험을 포함할 수 있지만 기간 집계와 최초 식사일 판단에서는 분리한다. 최초 판단은 선택 기간 이전의 아카이브도 확인한다. 같은 항목에 날짜 미확인 기록이 있으면 최초는 보류한다. ‘처음 기록’은 아카이브에서 확인되는 첫 경험이지 생애 최초 섭취가 아니다.

전체 반복 횟수는 독립 식사의 중복으로 판단할 수 있다. 기간별 반복은 앞선 경험이 입증되는 최소 횟수만 표시한다. 처음과 다시는 서로 배타적이지 않다.

날짜 구간은 로컬 달력의 `[start, end)`다. 이번 달은 오늘까지다. 변화 기본 범위는 최근 90일과 직전 90일이며 선택기에서도 이를 표시한다. 다른 기간 선택 시 같은 길이의 직전 기간을 사용한다.

### 감각·평가

감각 존재, 느낀 강도, 감각별 호감, 알맞음, 음식 전체 평가는 별개다. 강함을 좋음·과함·싫음으로 대체하지 않는다. 과거 강도 기반 `rating`을 만족도에 사용하지 않는다.

관찰은 현재 원본 revision과 일치하고 제외 대상이 아니어야 한다. 새 측정 경로는 직접 선택을 다시 파싱한 atom과 일치하는 관찰만 사용한다. 자유 회고는 원문으로 보존한다. 기존 발견이 사용하는 텍스트 근거는 기존 검증 정책을 따르며 새 직접 응답처럼 바꾸지 않는다.

감각 응답은 식사 단위로 중복을 제거한다. 한 식사에 서로 다른 평가가 있으면 ‘응답 나뉨’, 서로 다른 강도는 ‘여러 강도’다. 음식 전체 평가는 요리 단위다. 미응답은 중립·부정·0점이 아니다. 분모가 없으면 비율도 만들지 않는다.

## 3. 경험

히어로는 메뉴별 점 군집이다. 군집은 개별 메뉴, 점은 해당 메뉴가 등장한 식사다. 한 식사의 여러 메뉴는 각각 표시되므로 점 합계가 전체 식사 횟수는 아니다. 기본 6개 메뉴를 표시하고 초과 반복은 숫자로 보완한다.

### 측정 6종

| 카드 | 의미 | 필요한 입력·집계 | 가상 표시 예시 | 상세 |
|---|---|---|---|---|
| 기록한 식사 | 경험 규모 | 요리 ID, mealID, 확인 식사일. 독립 mealID 집계 | 32번의 식사 · 요리 기록 41개 | 식사별 요리·날짜·원본 |
| 기록한 메뉴 | 개별 메뉴 경험 | 식당 ID와 메뉴 ID 또는 그 식당의 입력명 | 메뉴 18개 | 메뉴별 식사 횟수와 기록 |
| 기록한 식당 | 식당 경험 범위 | 서로 다른 확인 지점 ID | 9곳 | 식당별 메뉴·식사. 방문 여부는 단정하지 않음 |
| 기록한 음식 종류 | 식당을 넘는 음식 범위 | 명시된 유효 분류 ID. 복수 분류 허용 | 11가지 | 분류에 연결된 메뉴·식당 |
| 처음 기록한 경험 | 새로 등장한 항목 | 전체 아카이브의 최초 확인 식사일이 기간 안에 있음 | 처음 기록한 메뉴 5개 | 메뉴/식당/음식 종류 전환, 첫 식사와 전체 연결 근거 |
| 다시 기록한 경험 | 반복된 항목 | 최초 이후 별도 식사가 선택 기간에 있음 | 다시 기록한 메뉴 7개 | 같은 3종 전환, 기간 반복·누적 횟수·타임라인 |

### 발견

| 카드 | 의미 | 필요한 입력·노출 조건 | 가상 표시 예시 | 상세 |
|---|---|---|---|---|
| 한 식당, 여러 메뉴 | 한 곳에서의 메뉴 경험 폭 | 같은 식당, 2번 이상 식사, 3개 이상 개별 메뉴 | 온담에서 4번의 식사에 메뉴 6개를 기록했어요 | 각 메뉴와 식사 기록 |
| 함께 기록한 메뉴 | 함께 등장한 메뉴 관계 | 같은 mealID에 두 메뉴가 공존한 식사 3번 이상 | 라멘을 남긴 5번 중 3번에 교자도 함께 남겼어요 | 함께/각각 기록한 식사 모두 |
| 여러 식당에서 만난 음식 종류 | 같은 음식 분류의 여러 식당 경험 | 동일 확인 음식 분류, 식당 3곳 이상 | 김치찌개 분류를 3곳에서 기록했어요 | 분류 근거와 실제 식당별 메뉴 |

위 수치는 노출 정책이지 통계적 유의성·신뢰도 기준이 아니다. 반복을 최애·선호·방문으로 해석하지 않는다. 저장·수정 후 조건이 달라지면 다시 계산한다.

‘처음 메뉴 목록’, ‘자주 기록한 식당’ 등의 단순 목록은 위 측정의 보기 또는 상세다. 별도의 같은 내용 발견으로 중복 생성하지 않는다. 경험의 폭 종합 점수도 만들지 않는다.

## 4. 감각

히어로는 감각별 기록 빈도 스펙트럼이다. 맛·향·식감·기타를 구별한다. 기타 속성을 식감으로 강제 분류하지 않는다. 강도는 별도 카드로 읽는다.

| 유형·카드 | 의미 | 필요한 입력·조건 | 가상 표시 예시 | 상세 |
|---|---|---|---|---|
| 측정 · 기록한 맛·향·식감 | 자주 관찰한 특징 | 감각 존재 관찰. 식사/감각별 1회 | 바삭함 7/12번의 식사 | 선택한 감각과 기록 근거 |
| 측정 · 어느 정도로 느꼈나요 | 강도 응답의 분포 | 감각에 연결된 강도. 여러 강도·미응답 별도 | 강함 3 · 중간 2 · 약함 1 · 미응답 1 | 당시 강도·부위·시점·원본 |
| 발견 · 함께 느낀 감각 | 음식 안의 감각 공존 | 같은 요리에서 두 감각이 존재하고 3번 이상 독립 식사 | 구운 향과 바삭함을 같은 요리에서 3번 남겼어요 | 두 감각을 함께 남긴 실제 근거 |

복수 감각이 동시에 존재하므로 합계 100%가 되는 도넛을 만들지 않는다. 같은 식사의 서로 다른 요리에서 각각 관찰한 감각을 한 조합으로 만들지 않는다. 감각 조합이 곧 선호 조합은 아니다.

‘내가 남긴 표현’은 새로운 측정 지표가 아니라 원문 탐색이다. 회고가 없을 때 사용자가 쓴 것처럼 문장을 합성하지 않는다.

## 5. 취향

히어로는 감각별 응답 분포다. 감각 평가가 없으면 음식 전체 평가를 명확한 라벨과 함께 보여줄 수 있다. 표본 수를 항상 제공하며 적은 응답을 보편적인 취향으로 승격하지 않는다.

| 측정 카드 | 의미 | 필요한 입력·집계 | 가상 표시 예시 | 상세 |
|---|---|---|---|---|
| 음식 전체는 어땠나요 | 요리 전체 만족 | 직접 전체 평가 5단계, 요리 단위 | 24개 요리 평가 · 좋음 12 · 매우 좋음 5 | 전체 평가별 원본, 미응답 분리 |
| 감각별 호감 | 맛·향·식감 자체의 평가 | 좋음/보통/아쉬움. 식사별 중복 제거 | 바삭함: 좋음 6 · 보통 1 | 긍정·중립·반대·혼합 응답 |
| 나에게 맞는 강도 | 선호하는 정도에 맞았는지 | 부족/알맞음/과함의 직접 응답 | 짠맛: 알맞음 2 · 과함 4 | 감각·강도·당시 조건·원본 |

반복된 평가, 여러 음식의 공통 취향, 음식 전체와 감각의 대조, 패턴 예외는 기존 개인 취향/발견 엔진을 재사용한다. 화면에서 별도 선호 점수나 예측 엔진을 추가하지 않는다. 기존 엔진의 근거·반례·판단 보류와 읽음/숨김 정책을 유지한다.

가상 발견 예: ‘구운 가지는 전체적으로 좋았지만 쓴맛은 아쉬웠어요.’ 같은 요리의 두 평가가 명시적으로 연결되어야 한다. 다른 요리의 전체 평가와 감각 평가를 섞지 않는다. 상세에서 두 평가와 원본을 함께 보여준다.

## 6. 맥락

상단에서 감각과 **감각 호감 / 알맞음**을 선택한다. 히어로는 선택한 감각의 조건별 평가 분포다. 한 조건만 있어도 측정 가능하다. 비교할 조건이 없다고 존재하는 반응을 숨기지 않는다.

| 측정 카드 | 의미 | 입력·집계 | 가상 표시 예시 | 상세 |
|---|---|---|---|---|
| 음식 종류별 반응 | 음식 분류별 평가 | 동일 감각·동일 평가 척도 + 저장 분류 | 샐러드 산미: 좋음 4 · 보통 1 | 해당 분류의 음식과 평가 |
| 느낀 부위별 반응 | 부위마다 남긴 평가 | 명시한 부위 + 감각·평가 | 소스의 단맛: 좋음 3 | 부위를 명시한 관찰 |
| 먹는 시점별 반응 | 첫입·후반 등의 평가 | 명시한 시점 + 감각·평가 | 첫입 기름짐: 좋음 3 / 후반: 아쉬움 2 | 시점별 응답과 식사 |
| 느낀 강도별 반응 | 강도와 평가의 연결 | 같은 선택·요리·감각·부위·시점에 연결된 강도와 평가 | 약한 산미: 좋음 3 / 강한 산미: 아쉬움 3 | 두 응답이 연결된 원본 |

조건별 측정은 관찰 분포다. 집단은 겹칠 수 있고 다른 조건은 통제하지 않았다. 조건 미응답은 가상의 집단을 만들지 않는다. 같은 선택과 연결되지 않은 강도와 호감을 식사 ID만으로 묶지 않는다.

조건 차이에 대한 설명은 기존 엔진이 허용하는 발견을 사용한다. 가상 예: ‘소스와 국물에서 산미 평가를 다르게 남겼어요.’ 비교 척도를 동일하게 유지하고, 같은 식사의 대응 관찰인지 서로 다른 식사 집단인지 상세에서 확인한다. 차이를 인과·최적 강도·조리 처방으로 바꾸지 않는다.

## 7. 변화

기본은 최근 90일과 직전 90일이다. 히어로는 선택 최근 기간의 최대 여섯 시간 구간에서 기록한 메뉴 수를 표시한다. 관찰 사이를 매끄러운 곡선으로 보간하지 않는다. 기록이 없는 건수 0, 연결 미확인, 평가 자료 없음을 구별하는 것이 설계 원칙이다.

| 측정 카드 | 의미 | 입력·집계 | 가상 표시 예시 | 상세 |
|---|---|---|---|---|
| 경험 범위의 변화 | 기간별 경험 구성 | 같은 길이 기간의 식사·메뉴·식당·음식 종류 ID | 식사 24→32번 · 메뉴 15→18개 | 양 기간 원본과 집계 단위 |
| 감각 기록의 변화 | 감각을 남긴 비중 | 분모는 감각 존재를 하나 이상 남긴 식사 | 산미 3/15번→12/24번 | 실제 분자·분모의 근거 |
| 호감 평가의 변화 | 비교 가능한 호감 분포 | 같은 식당 메뉴·감각·부위·시점·연결 강도 | 이전 좋음 3 / 최근 좋음 1·아쉬움 2 | 양 기간 전체 응답과 조건 |
| 알맞음 응답의 변화 | 같은 조건의 알맞음 분포 | 위 범위 + 부족/알맞음/과함 | 단맛 과함 3→알맞음 3 | 실제 응답과 원본 |

표본이 적으면 원자료를 보여주되 ‘반복 비교 자료 부족’을 명시한다. 강도 미확인·충돌은 별도 범위이며 동일 강도를 뜻하지 않는다. 같은 메뉴도 실제 재료·조리가 달라졌을 수 있으므로 기간별 반응을 입맛 변화로 확정하지 않는다.

기존 기간별 차이·재경험·회상 발견은 기존 엔진의 범위와 해석을 유지한다. 새로움을 위해 매일 문장을 임의 변경하지 않는다.

## 8. 노출 범위·중복·상태

새 경험 관계와 감각 조합은 선택한 측정 기간에서 계산한다. 취향·맥락·변화의 기존 발견은 읽음·숨김 정책을 따르는 전체 아카이브 대기열에서 가져온다. 화면에 **‘전체 기록 분석 · 선택 기간의 측정과 별도’**를 명시한다. 별도 범위를 같은 기간 분석처럼 표현하지 않는다.

새 발견은 기본 3개와 더보기다. 기존 발견의 상세·읽음·7일 숨김은 재사용한다. 신규 관계에 지속적 읽음/숨김 저장 정책을 임의로 추가하지 않았다. 경험의 단순 마일스톤 발견을 카테고리 상세에서 중복 재노출하지 않지만 기존 홈 스택의 다른 동작은 유지한다.

측정 19종: 경험 6, 감각 2, 취향 3, 맥락 4, 변화 4. 이는 항상 채울 데이터 수가 아니라 고정 측정 항목의 수다. 전체 기록 없음은 안내 하나, 특정 항목의 응답 없음은 해당 카드의 자료 없음, 발견 없음은 발견 미생성으로 처리한다. 모든 부족 상태를 카드 여러 장의 경고로 반복하지 않는다.

## 9. 카드와 상세 동작

카드는 제목 → 의미/기간 → 값·분포·목록 → 해석 범위 → 근거 진입으로 구성한다. 기존 TBFont·TBSpacing·TBRadius·TBColor를 사용한다. 긴 조건을 글자 축소로 숨기지 않는다. 기본 목록은 3개, 더보기로 확장한다.

행을 누르면 해당 데이터의 근거 시트를 연다. 최초·반복은 순서 확인에 필요한 전체 연결 기록을 포함하며 선택 기간 밖 자료라는 사실을 설명한다. 다른 카드의 집계 범위를 조용히 바꾸지 않는다. 원본 보기/수정으로 이어진다. 사진 유무는 데이터 기능을 바꾸지 않는다.

큰 글자에서는 경험 3종 전환을 메뉴형으로 바꾸고 시간축을 목록으로 읽는다. 색상만으로 구분하지 않으며 실제 값과 범례를 텍스트로 제공한다. 0개 구간이 사라져도 다른 평가의 명암 위치를 재배정하지 않는다. 실제 VoiceOver·큰 글자 화면 검증은 별도로 수행한다.

## 10. 입력 확보와 추가 수집

| 데이터 | 현재 처리 | 추가로 필요한 경우 |
|---|---|---|
| 식사·요리 ID | 기존 기록 사용 | 과거 서로 다른 ID를 같은 날짜라는 이유로 합치지 않음 |
| 식사일 | 확인 날짜만 기간 집계 | 미확인 날짜는 기존 원본 수정에서 확인 |
| 식당·메뉴 | 확인 식당 ID와 그 범위의 메뉴 | 이름만 남은 식당의 지점 연결 확인 |
| 음식 종류 | 저장한 유효 분류 ID | 세부 음식 단위 분류가 부족하면 분류 세분화·사용자 확인 |
| 직접 만든 요리 | 식사·요리 및 명시된 음식 분류에는 포함 가능 | 반복 요리 집계에는 명시적 출처·레시피 정체성이 필요. 식당 없음으로 추론하지 않음 |
| 감각·강도·호감·알맞음 | 현재 원본에 일치하는 직접 선택 | 새 평가를 강제로 수집하지 않음 |
| 회고·사진 | 원본에서 제공 | 사진·AI 요약만으로 새로운 응답을 생성하지 않음 |
| 방문·지역·동행·가격 | 이번 범위의 필수 입력 아님 | 해당 기능을 도입할 때 목적에 맞게 검토 |

‘새로운 수집이 없다’는 ‘모든 과거 기록이 이미 집계 가능한 상태’라는 뜻이 아니다. 미확인 정체성·분류가 채워진 것처럼 보여주지 않는다.

## 11. 구현 연결과 검증

- `HomeSensorySummarySection`: 고정 다섯 입구, 기존 질문·발견 스택 유지.
- `TDDataEngine`: Foundation 기반 순수 집계. 원본 변경 없음.
- `TDNativeAdapter`: 원본 revision·제외 관찰·직접 선택 atom·척도 검증.
- `TasteDataCategoryView`: 기간·감각·반응 선택, 측정·발견, 근거 탐색.
- `HomeArchiveDetailView`: 기존 9종 경로를 5화면으로 연결.
- `AppNavigation`: 화면과 내비게이션 제목 일치.
- `TDDataDetailSheet`: 현재 원본 기록 보기/수정.

입력·계정 세대·기간·선택·날짜·타임존으로 렌더 결과를 식별한다. 별도 순수 계산의 취소 또는 키 불일치 결과는 반영하지 않는다. 계정 변경에서 렌더·선택·상세를 폐기한다. 수정·삭제된 원본의 결론을 유지하지 않는다.

현재 등록된 홈 파일 안에서 계층을 분리해 Xcode source 등록 누락을 피했다. 나중에 파일을 분리할 때는 실제 프로젝트 등록도 함께 갱신한다.

```sh
python3 ios/Tools/validate-taste-data.py
# macOS + Xcode에서 실제 앱 빌드까지
python3 ios/Tools/validate-taste-data.py --native-build
```

스크립트는 제품 파일에서 코어를 추출해 회귀 테스트를 컴파일·실행한다. 별도 모형을 테스트하는 방식이 아니다. syntax parse·문자열 연결 검사·코어 실행·iOS 빌드·기기 화면 검증을 구분한다. PR CI는 코어 검사 이후 서명 없는 iOS Simulator 대상 빌드를 수행한다.

수동 확인 대상: 다섯 화면의 실제 데이터, 큰 글자·VoiceOver, 원본 수정/삭제, 계정 전환 중 상세 열림, 긴 이름·많은 기록·자료 없음·날짜 경계. 테스트 파일 또는 preview가 있다는 이유로 완료로 기록하지 않는다.

사용자 Mac의 미커밋 작업, main 병합, 앱 설치는 PR 생성만으로 완료되지 않는다. 실제 연결과 실행 여부를 별도로 보고한다.
