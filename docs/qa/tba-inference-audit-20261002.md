## F01. 감각의 소실에 대한 아쉬움을 감각 자체의 불호로 바꾼다

**우선순위: 높음. 분류: 재현된 의미 해석 결함. 확신: JS 실행 높음, iOS 동일 결과는 소스 근거.**

감사 입력:

> 처음엔 좋았는데 소스를 묻히니 바삭함이 죽어서 아쉬웠다.

실제 `parseByRules` 결과:

```text
texture.crisp / sensory_presence / true / target=sauce
texture.crisp / attribute_liking / negative / target=sauce
needsAI=false, unresolved=[]
```

소스를 묻힌 행위는 감각 변화의 조건인데 감각의 대상으로 선택된다. 바삭함이 줄어든 변화에 대한 아쉬움이 바삭함 자체의 불호가 된다. 추가로 격리된 JS 메모리 저장소에서 같은 합성 문장을 3개의 별도 식사로 저장·분석했다. 실제 저장 관찰을 거친 모델이 `texture.crisp`의 소스 조건과 전체 조건 모두 `direction=negative`를 만들었다. 근거 개수만 늘려도 이 의미 오류가 사라지지 않는다.

- **말할 수 있음:** “소스를 묻힌 뒤 바삭함이 줄어든 변화에 아쉬움을 남겼어요.”
- **말하면 안 됨:** “소스의 바삭함을 싫어해요.”
- **반대로 단정해도 안 됨:** 이 문장 하나를 곧바로 일반적인 “바삭함을 좋아해요”로 뒤집는 것.
- **완료 기준:** 변화 대상·조건·평가 대상을 보존하거나 모호한 호감 추출을 유보한다. `죽어서`, `눅눅해져서`, `덜해져서` 등 의미가 같은 독립 사례와 실제 감각 자체 불호 사례를 함께 검증한다.

근거: `scripts/tba-platform-pilot/rules.mjs:130`의 scope 패턴, `:244`의 범위 선택, `:256`의 조건 유보, `:280` 이후 감각/호감 추출. iOS 메모 진입 `SensoryAnalysisEngine.swift:63`, scope `:318`, 대응 추출 `:435`. 실제 결과 [A21](../../output/qa/tba-inference-audit-20261002/audit-probe-results.json), [격리 저장·분석 결과](../../output/qa/tba-inference-audit-20261002/parser-storage-results.json). iOS 메모 파서를 실행한 결과는 아니다.

## F02. 웹 타입 계산에서 별도 선택의 강도와 호감이 결합된다

**우선순위: 높음. 분류: 재현된 선택 연결 결함. 확신: 높음.**

각각 별도 식사인 2개 기록에 동일한 v2 버블을 서로 다른 인스턴스로 넣었다.

```text
선택 A: 강도 strong만 응답
선택 B: 호감 liked만 응답
카탈로그 ID·감각·대상·시점은 같고 selectionInstanceID는 다름
```

실제 v2 파서는 유효한 두 선택으로 받아들이며 `unresolved=[]`다. 개인 모델의 B 호감 단위에는 `intensity=null`로 남아 올바르게 분리된다. 반면 웹 `mainWing`에서는 A의 강도를 B에 붙여 `maximalist` 후보가 `repeated_support`, 지지 2식사, `eligible=true`가 된다. 전체 hero 상태는 이 사례에서 `ambiguous_main`이었다. **이 재현을 “강렬형이 단독으로 표시됐다”로 확대하지 않는다.**

- **말할 수 있음:** “A는 강하게 느꼈고 B에는 호감을 남겼어요.”
- **말하면 안 됨:** “강한 A를 좋아했다” 또는 두 사실을 강한 풍미 선호의 반복 근거로 삼는 것.
- **원인:** `nativeAnalysis.ts:348`의 scope가 `selectionInstanceID`를 누락하고, `:394`에서 이 scope로 강도·호감을 연결한다.
- **완료 기준:** 웹 타입·부재 배제·질문 답변 캐시의 정체성 규칙을 실제 선택 동일성 계약과 맞춘다. 같은 인스턴스의 올바른 연결, 다른 인스턴스의 분리, 검증된 부모/디테일 관계를 함께 검사한다.

근거: [실제 웹 결과](../../output/qa/tba-inference-audit-20261002/runtime/result.json)의 `instanceScope`, [실행 입력](../../output/qa/tba-inference-audit-20261002/runtime/probe.ts). 브라우저 UI 실행은 하지 않았다.

## F04. iOS의 가상 답변이 선택 인스턴스를 잃는다

**우선순위: 중간. 분류: 재현된 질문 계산 결함. 확신: 확인한 모델 함수 범위에서 높음.**

산미 호감 식사 3개 중 앞의 2개는 약한 강도, 세 번째는 강도 미응답이다. 각 선택에 정상적인 인스턴스 ID가 있다.

```text

v2 자료: 가상 응답 3개를 계산했지만 changedInterpretationCount = 0

```

`PersonalTasteQuestions.swift:56`은 임시 `selectionEvidence`를 새로 만들면서 인스턴스와 부가 메타데이터를 복사하지 않는다. 현재 `SensoryEvidenceLinkage.sameSelection`은 인스턴스를 비교하므로 모의 답변이 원선택에 연결되지 않는다.

- **말할 수 있음:** 실제 응답으로 조건 해석이 달라질 수 있는 질문이다.
- **말하면 안 됨:** 현재 모의계산 0을 이 질문의 실제 영향이 없다는 근거로 사용.
- **완료 기준:** 가상 응답과 실제 응답이 동일한 원선택의 정체성을 유지한다. 같은 값의 답을 넣었을 때 모의계산과 실제 재분석의 상태 변화가 일치해야 한다.

## F05. 개인 모델의 유보와 타입 화면의 성향 표현이 공존한다

**우선순위: 중간. 분류: 계층 간 표시 정책 불일치. 계산 오류로 판정하지 않음.**

같은 조건의 단맛 호감 2식사 + 불호 1식사를 실제 웹 분석에 입력했다.

```text
개인 모델: direction=null, counter_evidence_present, leave_one_meal_out_unstable
mainWing: romantic, status=mixed, eligible=true
hero: provisional_profile, label=로맨틱
```

타입 자격은 `호감 ≥ 2 && 호감 > 불호`다. 개인 모델은 별도의 최소 근거·반례·안정성 기준을 사용한다. 타입 코드가 계산을 틀린 것은 아니다. 다만 실제 iOS hero의 `provisional_profile` 문장은 “식사 기록에서 달콤한 맛을 즐기는 성향이 보여요”이고 반례나 잠정성을 그 문장에 드러내지 않는다.

- **허용할 수 있는 방향:** 타입을 현재 기록의 잠정 요약으로 유지하되 해당 문장의 범위와 예외를 명시한다.
- **다른 선택:** 타입의 자격도 개인 모델의 근거 정책으로 통일한다.
- **이번 감사의 권고:** 타입의 제품 역할을 먼저 결정한다. 표본 2회를 3회로 기계적으로 바꾸는 것만으로 의미 문제가 해결됐다고 보지 않는다.
- **완료 기준:** 같은 입력에 대해 왜 타입은 표시되고 개인 취향 가설은 유보되는지 사용자 문장과 내부 계약으로 설명할 수 있어야 한다. 반례가 있는 경우와 조건별 반전 사례를 포함한다.

## F06. 일부 의미 평가가 잘못 연결된 감각과 문맥을 성공으로 센다

## 추가로 추적할 좁은 경계

### N1. 질문 완료 판정의 인스턴스 누락

`AppModel.swift`의 `personalTasteQuestionIsAnswered` 내 선택 비교(최종 확인 시 2008–2013행)는 ID·종류·버전·문구·부모를 비교하지만 인스턴스를 비교하지 않는다. 실제 predicate에 합성 파서 출력을 주입하면 원질문 A에 다른 인스턴스 B의 응답만 있어도 true다. 공통 동일성 함수는 A/B를 false로 구분한다.

다만 실제 인라인 응답 적용은 `PersonalTasteQuestionAnswer.swift:89,95`에서 인스턴스를 검사한다. 따라서 **일반 인라인 답변을 하면 반드시 오완료된다는 결론은 철회**한다. 넓은 기록 편집 후 완료 경로에서 원질문이 잘못 해결되는지 실제 파서·저장 통합 재현이 필요하다. [범위가 제한된 실행 결과](../../output/qa/tba-inference-audit-20261002/question-evaluation/completion-results.json).

### N2. knownAt 인스턴스 누락 — 감사 중 수정 확인

초기 Swift `DiningMemoryContext.swift:109–120`은 sourceField의 type/id로 첫 선택을 찾아, A는 그대로이고 B만 수정한 경우 B의 알려진 시각을 A의 불변 상태로 판단할 위험이 있었다.

최종 재확인에서 함수에 `selectionInstanceID` 매개변수와 일치 검사가 추가됐고, `SensoryAnalysisEngine.swift:74,77`의 관찰·미해석 경로가 해당 ID를 전달했다. 따라서 이 항목을 현재 미해결 결함으로 세지 않는다. **Swift는 수정 소스 확인이며 수정 후 실제 기록 이력 실행은 미검증**이다. 웹은 A=t1/B=t2로 정상 갱신됨을 실제 v2 파서 경로에서 확인했다. 이 수정은 감사 외부에서 이루어졌다.

### N3. 검증된 강도 연결 옵션의 전달 범위

`personal-taste-model.mjs:95`, `PersonalTasteModel.swift:232`는 상위 모델에서 받은 `validatedIntensityLinks`를 fit 집계에 전달하지 않는다. 합성 probe에서는 같은 링크가 호감 단위에 쓰이지만 상위 snapshot의 fit 강도 조건에는 쓰이지 않고, 직접 `buildFitPatterns`에 옵션을 주면 조건이 생겼다.

현재 홈 관계 분석은 직접 API로 옵션을 전달하는 경로가 있으므로 홈 전체의 결함으로 확대하지 않는다. 내부 API의 일관성 문제로 낮게 분류한다. [보조 probe 결과](../../output/qa/tba-inference-audit-20261002/policy/tba-policy-audit-probe.json).

## 이미 작동하는 경계와 철회한 초기 발견

- 강도·알맞음·음식 전체 평가에서 감각 호감을 생성하지 않음.
- 같은 식사의 여러 요리를 독립 반복으로 세지 않음. 같은 ID 충돌은 임의 선택하지 않음.

- 완료 predicate의 합성 재현은 전체 사용자 흐름의 오완료로 확대하지 않았다.

## 검증 결과와 실자료 평가 설계

실행 결과 원본은 [증거 폴더 안내](../../output/qa/tba-inference-audit-20261002/README.md)를 따른다. 최종 회귀 로그·소스 해시가 이 보고서의 기준이다.

| 검사 | 결과와 범위 |
| --- | --- |
| 기존 Node 플랫폼·엔진 회귀 | **170/170 통과, 실패·skip 0.** 저장·수정·삭제·계약을 포함한 개발 검사이며 전체 제품 품질이 아니다. |
| 별도 감사 경계 검사 | **21개 중 19 통과, 2개 기준 위반**: A11 횟수 문장, A21 변화/평가 오귀속. 구현으로 정답을 생성하지 않고 금지 추론 기준을 적용했다. |
| 웹 실제 모듈 | 유효한 v2 입력으로 타입 정책 불일치·타입의 인스턴스 결합 재현. 웹 knownAt 최신 정상도 확인. |
| Swift Foundation | 현재 모델·질문 소스 컴파일로 가상 답변 영향 차이 재현. 별도 완료 predicate 실험은 파서 stub 한정. |
| 기존 감각 개발 리뷰 재실행 | 50사례, detail 16/42, 명확한 호감 7/15, 미해석 포함 39/50, 관계 자동 정확도 null. 제한된 `semanticSuccess` 2개이며 전체 정확도는 null. |
| 하지 않은 검사 | iOS 전체 빌드/XCTest/UI·실기기·Android·운영 API·실사용자 실험. |

최종 Node 회귀 중 감시한 주요 JS 소스 해시는 바뀌지 않았다. Swift의 AppModel·DiningMemoryContext·SensoryAnalysisEngine은 외부에서 변경되어 위의 소스 재확인과 N2 판정을 갱신했다. Node 통과를 변경된 Swift 코드의 검증으로 사용하지 않는다.

기존 합성 순차 평가의 자료 범위는 159식사/61 holdout, 산미 한 속성, 한 선택 ID, 제한된 대상·시점이다. 해당 시점 이후의 관찰·다른 사용자·같은 식사를 제외하는 방어가 있고, 앞서 공개된 응답을 나중 query에서 사용할 수 있는 순차 평가다. 이 조사에서 그 경로의 시간 누출은 발견하지 않았다. 그러나 query가 이미 감각 강도·대상·시점을 제공하므로 섭취 전 추천 평가가 아니다.

후속 독립 평가는 다음처럼 설계한다. 아래 규모는 확정된 검정력 기준이 아니라 첫 검토를 위한 제안이다.

1. **관계 의미 세트:** 실제 동의한 원문 또는 독립 작성 사례를 감각·호감·대상·시점·조건·변화·부재·타인 발화로 나눠 라벨링한다. 하나의 정답 문장 대신 허용 관계, 필수 보류, 금지 주장을 적는다.
2. **평가 분리:** 개발에 사용한 사례와 동결 평가를 분리하고, 사용자·식사·같은 원문 변형이 두 세트에 겹치지 않게 한다. 합성 세트는 데이터 누락·모순·수정 경계를 검증하는 별도 층으로 둔다.
3. **사람 검토:** 두 검토자가 독립 판정하고 불일치를 해소한다. 원문 자체가 모호하면 애매함을 정답 상태로 보존한다. 모델이 만든 답을 그대로 정답으로 사용하지 않는다.
4. **함께 보고할 지표:** 잘못 단정한 비율, 누락한 의미, 적절한 유보, 과도한 유보, 관계별 정확성, 삭제 후 잔존 주장, 원근거 복원 가능성. 출력을 적게 하는 모델이 무조건 유리해지지 않게 응답률을 함께 표시한다.
5. **질문 효용 실험:** 현재 facet 우선 정책, 영향 우선 정책, 질문하지 않음을 비교한다. 응답 완료·회상 가능성·사용자 부담·수정량·후속 해석 유용성을 따로 측정한다. 내부 해석 개수를 실제 효용의 정답으로 두지 않는다.

2. **문장·타입·질문 판단 일치:** F03/F04 수정, F05의 잠정 타입 역할 결정. 입력 하나에 대해 모델 상태·표시 문장·가상 답변·실제 답변 결과를 나란히 검증한다.
3. **평가기 보강 후 독립 평가:** F06의 오답 변형을 실패시키고, 기존 통과 수와 별도로 관계 의미·유보·사용자 효용을 평가한다. 그 결과를 얻기 전 최소 식사 수나 반례 정책을 성능 개선 목적으로 조정하지 않는다.

이번 산출물은 감사 결과다. 위 수정 작업을 수행하거나 실제 사용자 품질을 검증한 결과가 아니다.
