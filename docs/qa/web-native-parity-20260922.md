기준은 이 체크아웃 `ios/TasteBuddy`의 현재 작업 트리다. `ios/Reference/Native`의 과거 캡처나 별도 `Taste Buddy app` 체크아웃을 현재 모습으로 간주하지 않았다. 기존 네이티브·브랜딩·스플래시 변경을 보존했다.

## 데이터 경계

- `native_account_data.payload.values["tastebuddy.ios.dining-entries.v1"]`의 Swift `Data`는 base64로 인코딩된 UTF-8 JSON이다. `JSONEncoder` 기본 날짜는 **2001-01-01 기준 초**다. schemaVersion 1/2만 읽으며 그 외 버전이나 깨진 원본을 빈 기록으로 바꾸지 않는다.
- 네이티브 식사일은 `mealTime.source === user_confirmed`의 `start`만 사용한다. 확인 시각도 현재 이후이면 사용하지 않는다. 레거시 웹의 `scenario.completedAt`은 식사일로 승격하지 않는다.
- 식사당 여러 요리는 식사 수를 늘리지 않는다. 충돌하는 동일 ID의 원본은 관련 식사를 제외한다. 날짜가 서로 다른 식사 묶음은 날짜 미확인으로 분리한다.
- 네이티브의 명시적 식당 네임스페이스/ID·메뉴 ID·직접 요리 ID를 보존한다. 연결이 없는 네이티브 이름을 임의 식당/메뉴 식별자로 바꾸지 않는다.
- 감각/평가 집계는 기존 공통 선택 파서로 확인한 원응답만 사용한다. 자유 회고·생성된 설명·기본 별점·사진으로 호감이나 감각을 채우지 않는다. 자유 회고는 원본 검색/보기에서 보존한다.
- 웹의 예전 자동 추정 음식 종류와 기본 별점은 네이티브의 확인된 출처/직접 전체 평가와 같은 데이터가 아니다. 해당 근거는 누락 상태로 둔다.
- 네이티브 `TDNativeAdapter`의 분석 snapshot revision/보류 issue 전체 모델까지 동일하게 이식한 것은 아니다. 웹은 현재 원본의 선택 응답을 다시 검증해 집계한다. 전 엔진 동등성 검증은 별도 필요하다.
- 2차 코드에는 기존 네이티브 백업 RPC를 통한 저장 경로가 있다. 이번 검증 실행은 로컬·모의 전송 및 외부 API 차단 브라우저에서 수행했다. SQL migration 적용, 운영 배포, 실제 사용자 계정 원본 수정은 하지 않았다.

## 2차 반영: 입력과 원본 저장

### 사용자 흐름

- 가운데 `미식 기록 시작` 및 홈 CTA → 메뉴·사진 → 직접 전체 평가 → 기존 미각 버블 지도 → 버블/태그별 호감·강도·알맞음·대상·시점 → 확인·저장 → 나의 디시.
- 공개 검색의 기록 버튼과 식당/메뉴 상세에서도 새 기록기를 열며, 확인된 Kakao 장소 ID만 식당 연결로 전달한다. 이름만 있는 결과는 식당 ID를 만들어내지 않는다.
- `사진·메뉴만 먼저 저장`은 `captured` 상태다. 기록 횟수에는 포함되지만 아직 감각·호감 근거로 집계하지 않는다. 나의 디시의 `미각 기록 이어 쓰기`로 마저 작성한다.
- `이 식사에 메뉴 추가`는 새 기록 ID와 기존 mealID를 사용한다. 식사 시점은 유지하고 별개의 직접 요리 ID는 물려주지 않는다.
- 홈의 원본 근거/검색에서도 수정기를 연다. 에디터가 처음 연 원본을 expected 값으로 고정해, 백업 갱신 도중 열린 오래된 에디터가 새 원본을 덮지 못한다.

### 저장 계약과 경계

- `nativeRecord.ts`: 원본 UTF-8/base64, Swift 날짜, source fields 변경 이력, 알려지지 않은 필드 보존, 명시적 삭제 응답의 이전 이력 제거. 새 레코드의 호환 rating은 네이티브와 같이 0이며 직접 평가가 아니다.
- `nativeRepository.ts`: 계정 스냅샷의 다른 values/photoFilenames를 유지하며 원본 배열만 변경한다. 최초 계정 조회 실패/지원하지 않는 스키마/읽을 수 없는 원본을 빈 스냅샷으로 덮지 않는다.
- `nativeStorage.ts`: 계정별 IndexedDB. 사진 Blob과 원본 참조를 한 트랜잭션으로 저장한다. 네트워크 백업은 별도 잠금을 사용하고 로컬 저장을 막지 않는다.
- `nativeTransport.ts`: 소유자 세션 토큰을 작업별로 고정한다. 기존 미디어 업로드 임대와 private bucket을 사용한다. 사진 업로드가 실패하면 계정 스냅샷 저장으로 진행하지 않는다. 동일 이름 사진은 바이트 해시가 같은 경우에만 재시도 성공으로 취급한다.
- 백업에는 expected revision을 보내며 충돌 시 기기와 계정 스냅샷 모두 보관한다. 사용자가 계정 원본 사용을 선택해도 기기 변경은 복구 목록에 남긴다. 프로필·다른 values의 자동 병합은 하지 않는다.
- 서버가 저장한 뒤 응답만 유실된 경우 pending snapshot과 원격 revision/payload를 비교해 중복 생성 없이 조정한다. 그 사이 추가로 작성한 로컬 변경은 dirty 상태를 유지한다.
- 로그아웃은 계정별 로컬 원본을 유지한다. **계정 삭제 성공 이후에만** 해당 계정 archive·사진을 지우며, 삭제 표식을 같은 트랜잭션에 남겨 늦게 끝난 작업의 데이터 재생성을 차단한다.
- 첫 계정 원본 조회가 실패하고 캐시도 없는 경우 입력 시작을 막는다. 기존 캐시가 있으면 기기 기록은 계속 사용할 수 있다. 다른 guest/로그인 계정 원본을 자동 이동/병합하지 않는다.
- 사진 교체 전 파일의 자동 정리와 개별 원본 삭제 흐름은 아직 이식하지 않았다. 기존 원본/사진을 임의 삭제하지 않는다.

## 3차 반영: 나의 입맛과 개인 취향 해석

### 반영 범위

- `nativeAnalysis.ts`는 완료 원본에서 직접 전체 평가, 감각 선택, 자유 원문을 공통 규칙으로 읽는다. 미완료 캡처·충돌한 동일 원본은 분석하지 않는다. 불확실한 표현과 선택은 원문/확인 중 상태로 보존한다.

- 미각 타입은 네이티브 9개 범주와 식사별 지지/반대·동률·윙의 독립 근거 규칙으로 표시한다. 유형을 확률이나 고정 성격으로 표현하지 않는다.
- 조건별 해석은 관련 식사·반례·판단 유보를 보존하고, 알맞음 및 음식 전체/개별 감각 평가를 별도로 보여준다. 상세에서 비교와 원본 기록을 오가며 원본을 수정할 수 있다.
- ‘다음 선택’은 실제 저장 가능한 원출처의 누락된 항목만 보완한다. 선택 ID·버전·문구·연결 버블·부위/시점을 재확인하며 기존 응답, 중복 선택, 다른 기록에는 답변을 쓰지 않는다. 저장은 2차의 로컬 원자 저장/수정 이력/백업 경로를 사용한다.

## 4차 반영: 홈의 질문·발견 스택과 표시 이력

### 홈과 공통 질문 경로

- `HomeJournalStack`은 네이티브와 같이 발견을 먼저 배치하고 질문과 번갈아 섞는다. 접힘은 1장, 펼침은 3장이다. 작은 묶음에서는 같은 대상의 발견이 중복되지 않으며, 전체보기는 같은 큐를 24개씩 보여준다. 답변/보류/열람 후 남은 카드가 자동으로 채워진다.
- `JournalStackCard` / `NativeQuestionCard`를 홈과 나의 입맛에서 함께 사용한다. 질문 카드 본문을 누르면 선택지가 펼쳐지고, 답변 선택은 즉시 원출처에 저장한다. 메뉴·시점·부위, 원래 선택 문구, 확인한 식사일을 함께 표시한다. 사진이 없거나 아직 불러오지 못했으면 네이티브와 같은 seed 기반 장식 아바타를 쓴다.
- 질문 이력은 `tastebuddy.ios.personal-taste-question-progress.v1`의 base64 JSON에 저장한다. 현재 iOS `AppModel`이 분석에 사용하는 `local-owner`를 모델/질문 ID에 적용하고, 실제 저장소와 백업 소유자는 인증 계정별로 분리한다. 다른 계정 원본을 합치지 않는다.
- 최초 노출, 24시간 보류, 30일 기억나지 않음, 해결 후 24시간 유예, 미래 상태의 노출 보류를 반영했다. 이전 가족 단위 이력은 그때 이미 존재하던 출처에만 한 번의 7일 유예로 옮기며, 새 기록을 과거 답변으로 처리하지 않는다.
- 답변과 해결 상태를 같은 IndexedDB 트랜잭션에 저장한다. 이력을 읽지 못하거나 원출처가 바뀌었으면 원본과 처리 상태를 모두 유지한다. 되돌리기는 저장 당시 원본이 그대로일 때만 적용하고 현재 원본과 수정 이력을 사용해 기록을 갱신한다.
- 계정 백업에는 기존 CAS 경로를 사용한다. 실제 계정으로 서버 저장→iOS 복원까지 실행한 증거는 아직 없다.

### 발견 후보와 기기 이력

- 현재 네이티브 원본 경로에 연결한 종류는 **8개**다: 한 식당 여러 메뉴, 반복된 만족, 긴 기록 간격, 지난해 이맘때, 함께 기록한 메뉴, 여러 식당의 음식 종류, 익숙한 식당의 새 메뉴, 함께 느낀 감각.
- 식당 namespace/ID, 메뉴 ID 또는 연결된 메뉴명, 직접 요리 ID를 구분한다. 이름만 같은 미확인 식당을 묶지 않는다. 같은 식사의 여러 접시를 독립 식사로 세지 않는다.
- 직접 평가만 사용하며 자유 회고로 발견용 감각/호감을 채우지 않는다. 미응답·반대 기록을 분모/원본에서 지우지 않고, 같은 식사에 의미 미확정 선택이 있으면 해당 감각/평가의 발견을 보류한다. 시간 발견은 확인된 일관된 식사일만 사용한다.
- `.repeatedMenu`는 네이티브처럼 기존 측정과 중복되는 발견에서 제외한다. **아직 구현하지 않은 10종**은 공통 취향, 선호 강도, 조건별 차이, 다른 한 번의 경험, 전체/부분 대비, 재방문 평가 비교, 기간별 평가 변화, 새 메뉴의 익숙한 취향, 감각 비중 변화, 알맞음 변화다. 따라서 발견 전체 엔진의 완전한 동등성을 주장하지 않는다.
- 읽음은 의미 키에, 7일 숨김은 발견 ID에, 대상 냉각은 subject ID에 저장한다. 메모/사진/원본 revision이 바뀌어도 같은 의미는 읽음으로 유지하고, 다른 의미는 대상의 24시간 냉각 뒤 다시 후보가 될 수 있다. 한 달/최근 기간의 의미가 자정마다 새로 생기지 않도록 기간 키를 유지한다.
- 홈에서는 다양성을 고려한 최대 12개 발견 후보를 사용한다. 범주 상세에서는 대상 냉각을 적용하지 않고 읽음/미읽음을 나누되, 7일 숨김은 같이 적용한다. 현재 네이티브 원본을 쓰는 홈과 범주 화면이 같은 후보 생성기와 이력을 사용한다. 이전 웹 전용 기록은 기존 표시 경로를 보존했다.

## 7차 반영: 프로필 정보·사진의 네이티브 원본 저장과 복원

- 현재 Swift의 `UserProfileIdentity`, `NativeAccountSnapshot`, `saveProfileIdentity`, `saveProfileAvatarImageData`, `ProfileEditSheet.saveProfileEdit`, 공개 프로필 repository를 확인했다. 정보는 `tastebuddy.ios.profile-identity.v1`의 base64 UTF-8 JSON, 사진은 `tastebuddy.ios.profile-avatar-image-data.v1`의 **원본 이미지 바이트 base64**로 읽고 쓴다. 사진 바이트를 JSON 문자열로 한 번 더 인코딩하지 않는다.
- `nativeProfileIdentity.ts`와 `useNativeProfileIdentity.ts`를 App에 연결했다. 계정별 IndexedDB 원본을 먼저 읽으며 이름·버디네임·생년월일·성별/흡연 정보·식이제한과 사진을 프로필/요약/편집에 반영한다. 네이티브 원본이 있는 경우 그 값을 편집 출처로 사용한다. 다른 계정의 웹 전역 캐시를 네이티브 프로필로 자동 병합하지 않는다.
- 편집 저장은 `NativeRepository.changeSnapshot`의 **한 트랜잭션**에서 identity와 avatar를 함께 변경한다. 기존 식사 원본, 사진 파일 참조, 다른 metadata와 미래 확장 필드는 보존한다. 지원하지 않는 기존 문맥 응답이 편집 UI의 미선택으로 보이더라도, 명시적인 새 응답이 없으면 원값을 유지한다. 알 수 없는 식이제한은 ‘없음’으로 표시하지 않는다.
- 편집을 열 때 identity/사진의 현재 서명을 잡는다. 다른 탭에서 해당 값이 바뀌면 저장을 거절하고 작성 중인 문구를 유지한다. 식사 같은 무관한 metadata 변경은 최신 snapshot에 병합한다. 계정이 바뀌면 이전 편집을 현재 계정에 적용하지 않는다.
- 기존 웹 사진 편집 결과는 최대 512px JPEG로 변환해 UIImage가 읽을 수 있는 Data로 저장한다. 새 사진은 5MB 입력 제한과 계정 snapshot의 16MiB 제한을 검사한다. 이미 보관한 네이티브 사진은 변경하지 않으면 바이트 그대로 유지한다. 미리보기를 지원하지 않는 형식은 원본 보관 안내와 교체/삭제 경로를 제공한다. HEIC 등 모든 iOS 사진 형식의 브라우저 미리보기를 구현한 것은 아니다.
- 사진 교체·삭제는 최종 저장 버튼을 누를 때 적용한다. 삭제는 avatar key만 제거하며 식사 사진이나 기존 공개 미디어 파일을 삭제하지 않는다. 삭제 후 이전 웹 캐시 사진이 다시 나타나지 않는다. 아직 네이티브 프로필이 없는 기존 웹 사진은 사용자가 저장할 때 준비에 성공한 경우에만 함께 보관한다.
- 기기 저장 후 기존 계정 백업 RPC/CAS 경로가 동작한다. revision 충돌·응답 유실·네트워크 실패는 기존 원본 보존 규칙을 따른다. 손상된 원격 프로필/사진 envelope는 정상 로컬 snapshot을 대체하기 전에 거절한다. 기기 보관과 계정 백업 확인 상태를 시트에서 구분한다.
- 공개 프로필 반영은 별도 단계다. 현재 네이티브처럼 사용자 ID를 지정한 upsert로 이름/버디네임을 반영하고 auth metadata도 갱신한다. 허용된 계정의 토큰을 고정하고 계정 전환을 재확인한다. 생년월일·성별·흡연·식이제한·사진 Data는 공개 프로필 요청에 넣지 않는다. 공개 반영에 실패해도 기기 원본은 유지되며 재시도할 수 있다. 개인 프로필 사진과 기존 공개 avatar 저장소는 별개다.
- 사진 편집 컴포넌트의 기존 타입 오류 4개도 수정했다. 기존 측정/선호 설문 원본과 분석의 선호 카드 전체를 native identity로 대체하지 않았다.

## 8차 — 저장 목록 생성·이동·식당 저장 해제 (2026-09-22)

### 현재 네이티브와 비교한 구현

- 기준은 `AppModel.swift`의 `createBookmarkList`, `saveRestaurantBookmark`, `ensureRestaurantBookmark`, `removeRestaurantBookmark`와 `RestaurantBookmarkNativeSheet`다. 네이티브 삭제는 **저장한 식당 해제**이며, 리스트 자체 삭제/이름 변경 mutation은 없다. 지원되지 않는 리스트 삭제는 추가하지 않았다.
- 프로필 저장 목록에서 새 리스트 생성, 실제 식당 수, 개별 식당의 리스트 이동/저장 해제를 연결했다. 상세 화면 및 통합 검색의 바로 저장도 같은 계정별 원본을 사용한다. 북마크 열기는 네이티브처럼 미저장 식당을 기본 목록에 저장하며, 기존 식당을 다시 여는 것만으로 이동하거나 변경 이력을 추가하지 않는다. 선택된 리스트를 다시 누르면 저장은 유지한 채 기본 목록으로 옮긴다.
- 이름 제안, 공개/비밀 설정, 현재 네이티브 음식 아이콘 14개·미각 색상 6개를 연결했다. 저장/취소는 하단에 고정한다. 네이티브의 `coverIconID`, `coverTasteID`, `isPrivate`, 문자열 ID와 2001년 기준 Swift Date를 그대로 쓴다. 표지 선택은 현재 웹 시트 안에 펼쳐지며 네이티브의 별도 표지 오버레이 전환/토스트 모션까지 동일하다는 의미는 아니다.
- `nativeBookmarks.ts`는 lists/records/saved IDs/pending mutations를 같은 IndexedDB snapshot 트랜잭션에 보관한다. 새 리스트 생성+현재 식당 이동도 한 트랜잭션이다. 원본의 알 수 없는 필드, 다른 식당, 프로필, 식사, 사진 참조를 보존한다. 식당 이름으로 합치지 않는다. 이름 미확인 과거 ID도 관리/해제가 가능하다.
- 열린 편집창은 대상 식당의 원본 서명을 고정한다. 같은 식당의 다른 탭 변경이나 목적 리스트 변경은 거절하며, 무관한 식당 변경은 허용한다. 실패 시 새 리스트만 남기는 부분 저장 없이 초안을 유지한다. 계정 전환 시 상세/검색/저장 목록 컴포넌트를 초기화한다. 손상된 원격 북마크 metadata는 정상 로컬 원본을 교체하기 전에 거절한다.
- 네이티브 pending의 `createList`/`saveBookmark`/`removeBookmark`, UUID, 시각을 함께 보관한다. 전체 snapshot 백업 성공만으로 pending을 비우지 않는다. 현재 네이티브 bookmark 전용 resolve/export/apply/markSynced 메서드의 활성 호출 경로는 찾지 못했으며, 별도 동기화 endpoint를 임의로 만들거나 기존 웹 테이블의 전체 삭제→재삽입으로 연결하지 않았다.
- 기존 웹 localStorage 목록은 ‘이전에 저장한 목록’에서 유지한다. 소유자 불명인 과거 데이터를 네이티브 계정 원본으로 자동 합치지 않는다. 신규 root는 빈 네이티브 원본에서도 리스트를 생성할 수 있다.
- 공통 Drawer의 실제 설치 모듈 import와 union props 조합 타입을 수정했다. 실행 라이브러리는 동일한 vaul이며 기존 시트도 사용하는 타입 오류를 해결했다.

### 남은 경계

- 실제 로그인 계정의 백업 RPC, 다른 iOS 기기의 수신, pending 전용 송수신은 검증하지 않았다. 백업 검증은 모의 전송과 Swift Codable 호환성에 한정한다.
- 공개 장소와 기존 네이티브 식당 ID의 전체 대응표는 없다. 현재 웹 상세는 원본 kakaoPlaceId가 있으면 그 ID, 없으면 상세 모델 ID를 쓴다. 이름으로 기존 네이티브 식당을 추정 병합하지 않는다. 네이티브 저장 식당에서 공개 장소 상세로의 연결과 과거 웹 목록의 명시적 소유자별 이전은 후속 범위다.
- 별도 표지 선택 오버레이/토스트/미세 모션, 전체 선호 설문·알레르기 원본 통합은 남는다. iOS 앱 빌드·기기 UI 및 운영 배포는 수행하지 않았다.

## 9차 — 저장 식당에서 장소 상세·미식 기록으로 연결 (2026-09-23)

### 차이 및 구현

- 네이티브 `AppRouteDestinations.swift`는 저장 목록의 식당 ID를 `.restaurant(id:)`로 전달한다. 현재 저장 목록의 임의 `mingles` fallback/고정 수치는 복제하지 않는다. 웹의 이전 단계는 저장 이름·셰프·일자 조회 및 목록 관리까지만 연결되어 있었다.
- `nativeSavedPlace.ts`를 추가했다. 현재 카탈로그의 restaurantSlug, 기존 웹 검색 결과의 식당/셰프/메뉴 ID, 예약 결과 ID, 보관된 Kakao 장소의 숫자 provider ID를 정확히 비교한다. 저장된 **이름 자체를 검색키로 쓰지 않는다**. 과거 웹의 이름 파생 ID는 현재 카탈로그 후보가 하나일 때만 허용하며, 정규화된 이름이 같아도 서로 다른 식당 slug가 있으면 모호함으로 처리한다.
- Kakao cache는 source/숫자 ID를 검사하고 지도 URL은 해당 ID로 직접 구성한다. 임의 캐시 URL을 그대로 링크하지 않는다. 동일 provider ID라도 이름/주소 등 보관 내용이 충돌하면 임의 항목을 고르지 않는다. 캐시가 없거나 손상되어도 저장 원본은 그대로 남는다.
- 확인된 식당을 누르면 상세를 열고, 뒤로 가면 보던 개별 리스트로 복귀한다. 같은 이름의 식당은 확인된 주소로 구분한다. 미확인/충돌 식당은 원래 정보와 관리 화면을 유지한다. 카탈로그가 늦게 도착해 정보가 확인되면 해당 정보 화면에 상세 진입 버튼이 나타난다.
- 상세에는 별도의 `nativeBookmarkID`를 전달한다. 화면용 ID나 공개 장소 ID로 기존 저장 ID를 바꾸지 않는다. 상세/북마크를 열기만 하면 원본과 pending은 바뀌지 않으며, 저장 해제는 정확한 원본 ID만 대상으로 한다.
- 이 경로는 저장 원본에 연결된 확인 가능한 정보만으로 상세 모델을 만든다. 확인되지 않은 매칭률·친구 평가·전체 평판은 `—`, 사진과 메뉴·영업시간은 임의 기본값으로 채우지 않는다. 일반 상세의 이름 기반 장소 재검색도 이 경로에서는 실행하지 않는다. Kakao 정보는 보관된 자료임을 표시하며 현재 정보는 지도에서 확인하도록 한다.
- 상세의 식사 기록 버튼은 기존 네이티브 미식 기록 편집기를 연다. 식당 이름과 원래 식당 ID를 전달하고, 실제 Kakao ID가 있을 때만 Kakao namespace를 사용한다. 저장 후 ‘나의 디시’로 이동하는 기존 흐름을 유지한다.

### 검증

- 정확한 slug/과거 검색 ID/예약 ID/provider ID, 동명 식당, 충돌된 카탈로그·캐시, namespace 충돌, 안전한 링크, 누락·손상 캐시, 원본 불변 테스트 **12개 추가**. 저장·프로필·기록 관련 회귀 포함 **96개 통과**.

- 추가 합성 카탈로그에 네이티브에도 존재하는 `onjium` 식별자를 사용해 상세·북마크 ID 보존을 확인했다. 이는 실제 온지음의 현재 장소 정보를 확인한 것이 아니다. 상세에서 합성 메뉴를 저장하고 `restaurantID=onjium`, 음식 출처 restaurant, 잘못된 Kakao namespace 없음, ‘나의 디시’ 도착을 확인했다.

### 남은 경계

- 연결 범위는 현재 카탈로그/예약 자료 및 기기에 보관된 Kakao 결과다. 다른 기기에서 받은 북마크에 대응하는 카탈로그나 장소 캐시가 없으면 미확인 상태로 남는다. provider ID로 서버에서 새 장소를 받아오는 전체 경로 및 이름 파생 ID의 명시적 이전은 후속 범위다.
- 전체 식당 ID 대응표, 기존 웹 목록의 소유자별 이전, 네이티브 별도 표지 선택 오버레이·토스트·모션, 전체 선호 설문/알레르기 원본 통합은 남는다.
