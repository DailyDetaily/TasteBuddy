# TBA 데이터 플랫폼: 규칙 우선 정제와 다양한 해석 파일럿

작성일: 2026-09-06 · 버전: 0.4 · 상태: 파일럿 검증 이력. 최신 감각 v2·앱 검증은 후속 문서 참조, 실제 API 의미 정확도 미검증

후속 [개인 취향 분석 엔진 v1](./tba-personal-engine.md)은 이 저장·정제 경로를 재사용해 실제 입력 구분, 디스크 저장, 개인 관계 인사이트, 메인·날개와 개인별 서술을 연결한다. 아래 가상 시나리오는 규칙 v3에서도 기존 근거 수와 출력 수를 유지한다.

이 파일럿은 [플랫폼 설계](./tba-data-platform-architecture.md)의 첫 구현이다. 최우선 목표는 **개인 취향 이해와 다양한 해석·인사이트 제공**이며, 비슷한 입맛 그룹 연결과 그 그룹의 식당·메뉴 추천은 후속 단계다. 저장소에 있는 **실제 음식 자료 7개**를 출처와 함께 읽고, **명시적으로 만든 가상 사용자 기록**을 별도의 PostgreSQL 엔진에 연결한다. 음식 지식과 개인 감각·호감을 구분해 저장·수정·삭제하고, 정제한 같은 근거를 여러 출력에 재사용한다.

v2는 **845개 표현의 의미사전과 짧은 글 규칙을 먼저 적용하고, 문맥 연결이 필요한 부분에만 AI를 호출하는 경로**를 추가한다. 실제 사용자 자료, 운영 Supabase, 앱 UI는 연결하지 않는다. 예측 모델 학습·추천 성능·실제 AI 모델 정확도는 검증 결과에 포함하지 않는다.

최신 `tba-rules/4`로 결과 JSON을 재생성했다. 아래 61개·77개 수치는 당시 검증 이력이며, 최신 결과는 [감각 모델과 앱 연결](./tba-native-sensory-integration.md)을 참조한다.

실제 모델 검증은 `OPENAI_API_KEY`를 안전하게 설정한 셸에서 다음 명령으로 별도 실행한다. 키 값은 출력하거나 결과 파일에 보관하지 않는다. `TBA_AI_MODEL`로 모델을 교체할 수 있으며 결과는 표준 출력으로 반환한다.

```bash
node scripts/tba-platform-pilot/live-ai-validation.mjs
```

출처마다 파일 해시를 기록하고, 각 주장에는 원본 ID 선택자, JSON 위치, 해당 레코드의 SHA-256 해시, 필드, 실제 값을 보존한다. 검토한 7개 레코드가 바뀌거나 사라지거나 중복되면 실행이 실패하여 재검토를 요구한다. 검토 범위 밖 레코드의 변경은 선택한 음식의 의미를 바꾸지 않는다.

카탈로그의 빈 필드와 없는 측정값은 결측이다. 재료가 없거나 물질 함량이 0이라는 의미가 아니다. 음식에 관한 자료만으로 감각 평가·개인 호감·실제 판매 메뉴·오늘 제공된 한 접시를 만들어 넣지 않는다.

## 3. 실제 자료가 드러낸 설계 요구

총 9개 검토 항목을 남긴다. 이 수는 고른 사례의 발견 수이며 전체 데이터셋의 오류율이 아니다.

| 관찰 | 파일럿 처리 | 아키텍처에 필요한 계약 |
| --- | --- | --- |
| 가루장국은 분류에 비가열·절임, 조리 원문에 삶기·끓이기가 함께 있음 | 두 주장을 보존하고 둘 모두 `contested_source_conflict`로 표시 | 출처가 있어도 주장끼리 충돌할 수 있으므로 주장 단위 상태가 필요 |
| 가자미미역국 두 원본의 이름은 같고 레시피 구성이 다름 | 원본 ID가 다른 두 레코드 유지 | 이름 중복 제거와 음식 동일성 판단은 별도 작업 |
| 가례불고기의 기존 연결에 갑각류·국물 조리가 들어 있음 | 원문에 채택 근거가 없음을 기록하고 기존 연결을 가져오지 않음 | `굵게` 속 `게`, `설탕` 속 `탕` 같은 부분문자열은 재료·조리 근거가 될 수 없음 |
| 홍연어가 패류 및 소고기 FoodOn 개념 3개와 연결되어 있음 | 기존 ID·대상 이름·원문을 검토 기록에 보존 | 상위 분류 이름과 영문 단어 일부를 개별 재료로 확정하지 않아야 함 |
| 에스프레소가 찻잎과 연결되어 있음 | 차류 분류만으로는 찻잎 포함을 확정할 수 없다고 기록 | 분류, 재료, 실제 제공 음식의 구성을 구분해야 함 |

이 검증은 기존 데이터 파이프라인을 고치거나 전체 FoodOn 관계를 복원한 결과가 아니다. 선별한 실제 자료에서 근거가 부족한 연결을 보류하고 충돌을 손실 없이 표현하는 첫 사례다.

## 4. 845개 의미사전과 호출 판단

원본 [`tba-bubble-atlas.json`](./tba-bubble-atlas.json)의 ID·라벨·버전을 보존하고 별도 의미사전에 연결한다. `tba-semantic-lexicon/2`의 845개 항목은 **해석 가능 503개, 일부 미확정 52개, 미확정 290개**다. 각 항목에는 감각·강도·호감·선호 수준·대상·시점 정의 또는 빈값, 판단 이유와 금지하는 추론이 있다. 이 상태는 파일럿의 언어 해석 정책이며 감각 과학의 확정 분류나 845개 표현 전체의 실사용 정확도를 뜻하지 않는다.

`parseByRules()`는 관찰, 미확정 부분, 호출 필요 여부·사유, 사전·규칙 버전을 반환한다. 원문의 정확한 구절과 JavaScript UTF-16 기준 위치, 선택지 ID, 적용 규칙을 함께 보존한다. 어휘 지도상의 부모 관계나 미선택 항목에서 관찰을 만들지 않는다.

| 원문에서 확인한 상태 | 처리 |
| --- | --- |
| 검토된 표현·활용형·부정·대상·시점으로 의미가 결정됨 | 규칙 관찰 저장, API 0회 |
| 정보는 있지만 대명사·조합·문장 연결을 규칙으로 해결하지 못함 | `needsAI`로 표시하고 별도 호출 경로에서 처리 |
| `깔끔했어요`처럼 원문 자체의 정보가 부족함 | 미확정 보존, API 0회, 필요할 때 선택적 확인 후보 생성 |
| 타인의 평가·외부 설명·무관한 내용 | 본인의 감각 관찰로 만들지 않고 원문 보존 |

감각의 강함을 호감이나 선호 수준 초과로 바꾸지 않는다. `촉촉한`을 육즙으로, 단독 `톡 쏘는`을 탄산으로, 복숭아 향의 비유를 복숭아 재료로 확장하지 않는다. `전체적으로 좋았어요`는 음식 전체 평가이며 시점은 미언급이다. `처음엔`은 식사 초반 `early_meal`, 명시한 첫입·첫모금은 `first_bite`로 구분한다. `끝에 남는 맛`만으로 식사 후반이나 삼킨 뒤를 정하지 않는다.

## 5. 사용자 기록과 AI 추출의 수명주기

음식은 실제 자료지만 사용자는 가상이다. 기존 v1 기준 시나리오의 유효 근거는 **4개 경험, 3개 식사, 8개 관찰**이다. 이 기준 시나리오는 기존 저장·수정·삭제 동작의 회귀 확인용으로 유지한다.

| 가상 입력과 변경 | 남는 의미·동작 |
| --- | --- |
| 감자튀김: 전체 “좋았어요”와 “바삭한” | 전체 호감과 바삭함의 보고를 따로 보존. “바삭해서 좋아했다”는 이유를 생성하지 않음 |
| 가례불고기: 전체 “아쉬웠어요”와 “진한 감칠맛” | 전체 부정, 감칠맛 존재, 표현 척도에서 강함을 구분. 감칠맛 회피를 지지하는 직접 근거는 없음 |
| 여기에 감칠맛 자체는 “좋았어요” 추가 | 전체 평가는 그대로 두고 감칠맛 회피 후보에 반대 근거를 연결해 `contested`로 표시 |
| 홍연어: “깔끔한” | 낮은 지방감이나 짧은 여운을 임의로 채우지 않고 표현을 미확정으로 보존 |
| 에스프레소: 전체 평가 수정·같은 값 재저장·훈연향 선택 취소 | 현재 전체 평가는 하나만 유지하고 취소한 감각을 활성 관찰과 해석에서 제외 |
| 별도 가상 경험 삭제 | 원문 이벤트·답변·관찰·해석·의존 관계가 실제로 0행이 되고 내용 없는 삭제 표식과 재시도 영수증만 유지 |

`clear`·`remove`는 선택 취소로서 과거 버전을 비활성화한다. 답변 원문을 모든 이력에서 지우는 별도 삭제 API는 구현하지 않았다. `delete`는 경험 전체의 원문과 파생 자료를 물리적으로 삭제한다. 보고서 생성 직전의 현재 상태를 다시 조회하여 이미 삭제한 경험의 원문이 결과에 남지 않게 한다.

v2는 안정적인 `answerKey`별로 활성 답변을 관리해 같은 질문 종류에서도 음식 전체·소스·튀김옷·시점별 답변을 함께 보존한다. 기존 입력은 질문 ID를 기본 키로 사용한다. 한 답변의 수정·취소는 그 답변에 연결된 근거에만 적용한다.

원문과 규칙 추출 결과를 먼저 트랜잭션으로 저장한다. `processAnswerAI()`는 트랜잭션 밖에서 `resolveWithAI()`를 호출하고, 응답이 돌아오면 소유자·경험·답변 키·원문 해시·현재 버전을 다시 검사한다. 수정·삭제 후 도착한 결과는 적용하지 않는다. 같은 원문·질문·범위·사전·규칙·프롬프트·모델 조건의 요청은 메모리 캐시를 재사용한다. 경험 삭제 시 관련 캐시도 제거한다.

초기 설정은 `gpt-6-astra`, `medium`이며 교체할 수 있다. Responses API의 엄격한 JSON 스키마와 별도로 원문 인용·허용 속성·값·척도·대상·시점·조합 구성 및 규칙과의 충돌을 검사한다. 거부한 의미는 미확정으로 남긴다. API 오류·시간 초과·불완전 응답에도 원문과 규칙 관찰을 유지한다. 구조화 출력은 형식 계약이며 의미 정확도를 보장하지 않는다. [OpenAI 구조화 출력 문서](https://developers.openai.com/api/docs/guides/structured-outputs)

모델이 추출한 관찰에는 `model_extracted_unconfirmed`를 표시한다. 명시적인 선택, 규칙으로 추출한 문장, 모델 추출과 사용자 확인을 구분한다. 기존 DB 요약도 모델 근거만 있으면 확인 전 후보로 표시하고, 같은 의미에 명시적인 응답이 추가되면 모든 원문 참조를 보고 상태를 갱신한다. 감칠맛 검토 가설의 직접·반대 지지에는 미확인 모델 관찰을 넣지 않고 별도 후보 참조로 보존한다. 조회·정제·해석 재생성은 저장한 추출 결과를 검증하며 API를 호출하지 않는다.

## 6. 정제한 동일 근거에서 다양한 출력 생성

실제 실행 경로는 `currentEvidenceRows(owner)`와 `currentUnresolvedRows(owner)`를 조회한 뒤 `normalizeEvidence(rows, { unresolvedRows }) → buildInsightViews(normalized)`로 이어진다. 현재 유효 관찰에 원답변·식사·음식·추출 결과를 연결하고 종류·속성·값·척도·대상·시점과 원문 구절의 일치를 검사한다. 서로 다른 사용자의 행을 한 개인의 근거로 섞는 입력은 거부한다.

정제 결과는 원문·질문·선택지 버전·출처·감각·강도·호감·음식·대상·시점·기록 시각과 추출·확인 상태를 보존한다. 명확한 자유문장은 관찰로 분해하고 남은 모호함은 별도 자료로 유지한다. 정제·출력 생성은 입력 객체나 DB 원문을 변경하지 않는다.

| 기존 v1 출력 종류 | 기준 시나리오의 산출물 수 | 제공하는 내용 |
| --- | ---: | --- |
| 경험 요약 | 4 | 각 음식의 전체 평가·감각·직접 호감·미확정 표현 |
| 속성별 프로필 | 2 | 바삭함·감칠맛의 보고와 직접 호감을 분리한 범위별 자료 |
| 평가 공존 해석 | 2 | 전체 평가와 감각 보고 또는 부분 호감이 함께 있다는 해석. 원인을 확정하지 않음 |
| 선택적 확인 후보 | 3 | 표현의 뜻, 직접 감각 호감, 전체 평가의 미확정 이유를 확인하는 후보. 자동으로 모두 묻지 않음 |
| 그룹 비교 준비 특징 | 7 | 실제 그룹 계산 전의 음식 전체 평가·직접 감각 호감·감각 맥락을 구분한 자료 |

총 18개는 여러 종류의 산출물을 합친 수다. 그룹 비교 특징과 질문 후보까지 포함하며, 18개의 새로운 개인 취향이나 독립적인 발견을 뜻하지 않는다. **원래 근거는 4개 경험·3개 식사·8개 관찰로 유지된다.** 기존 `currentPersonalEvidence.interpretations`의 9개 행과 새 `insightViews`를 합산해 사용자 근거 수로 사용하지 않는다.

각 뷰와 하위 사실에는 `observationRefs`, `scope`, `ruleVersion`, 공통 `evidenceSetHash`가 있다. 소유자도 출력 범위와 뷰 식별자에 반영한다. 수정·선택 취소·삭제 후 같은 생성기를 다시 실행하면 관련 근거가 모든 출력에서 제거된다. 이 파일럿은 결과를 생성할 때 재조회하며, 운영 캐시·비동기 게시의 자동 무효화는 후속 구현이다.

| 출력 | 해석 범위 |
| --- | --- |

일반화된 개인 선호·인과 설명·확률·장기 추세·실제 입맛 그룹·추천 결과는 생성하지 않는다. 출력 개수는 원래 경험이나 독립 표본 수를 늘리지 않는다.

산출물은 경험 요약 8개, 속성 프로필 9개, 맥락 해석 9개, 시점 비교 3개, 대상 비교 1개, 반복 경험 비교 1개, 조합 해석 1개, 선호 수준 해석 2개, 확인 후보 15개, 그룹 비교 준비 특징 30개로 총 **79개**다. 질문 후보와 준비 특징을 포함한 출력 수이며 개인 취향 발견 79건을 뜻하지 않는다. AI 경로에는 수작업 응답 2개를 넣었고 실제 API 호출은 0회다. 사용자 확인 전 모델 해석과 기존 v1 근거 수를 별도로 유지한다.

## 8. 다음 단계로 넘기는 조건

운영 구현 전에는 실제 인증 주체·접근 제어, DB outbox와 작업 처리기, 오프라인 충돌 처리, 미디어와 캐시까지 포함하는 삭제 경로를 별도로 구현해야 한다. 이 파일럿의 메서드에 사용자 ID를 전달하는 것은 실제 로그인·권한 검증을 대신하지 않는다.

예측 시점보다 늦은 입력을 제외하는 검사와 과거의 상태를 그대로 재생하는 기능은 다르다. 수정·삭제 전 과거 자료를 재현하려면 시점별 `FeatureSnapshot`과 자료 수명주기 정책이 더 필요하다. 삭제한 자료를 평가를 이유로 무조건 보존하지 않는다.

이번 `recordedAt`은 가상 입력에 고정한 검사 시각이다. 실제 서비스에서는 클라이언트가 입력한 식사 시각과 서버가 처음 받은 시각을 구분하고, 당시 사용 가능했던 음식 지식의 버전까지 스냅샷에 포함해야 한다.

다음 검증은 실제 API 반환의 의미 정확도, 기준 예문을 보고 수정하지 않은 별도 평가 문장, 동의한 실제 기록의 근거 충실도·해석 유용성·사용자 이해다. 미확정 어휘와 음식 연결도 검토 근거가 생길 때 확장한다. 개인 해석 경험을 마련한 뒤 그룹 연결을 검증하고, 그룹 기반 식당·메뉴 추천을 추가한다. 미래를 예측하는 모델에는 별도 시간순 평가를 적용한다. 가상 기록에서 저장·정제·출력 계약이 통과했다는 사실을 실제 사용자의 취향 이해나 추천 성능이 입증된 것으로 해석하지 않는다.
