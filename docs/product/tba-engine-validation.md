# TBA 개인 엔진 추가 평가

작성일: 2026-09-06 · 범위: API 연결 전 오프라인 계약 평가

추가 가상 시나리오 **12개가 모두 통과**했다. 같은 타입 조합에서도 실제 원문 속 감각이 다르면 서로 다른 설명 자료와 근거 요약을 만든다. API 연결은 사용자 요청에 따라 후속 단계로 남겼다.

[엔진 사용법](./tba-personal-engine.md) · [전체 결과와 원문](./tba-engine-evaluation-results.json) · [평가 사례](../../scripts/tba-engine/validation-cases.mjs) · [평가기](../../scripts/tba-engine/evaluate.mjs)

## 실행

```bash
node --test scripts/tba-engine/*.test.mjs
node scripts/tba-engine/evaluate.mjs --output docs/product/tba-engine-evaluation-results.json
```

평가기는 환경변수의 API 키를 읽지 않으며 `--live`를 지원하지 않는다. 실제 저장·규칙 정제·인사이트·타입·근거 요약을 거치고 네트워크 호출 횟수를 별도로 검사한다. 실행 중 생성한 메모리 DB는 종료 시 닫는다. 운영 DB나 앱에는 쓰지 않는다.

## 확인한 조건

| 사례 | 검사한 내용 | 결과 |
| --- | --- | --- |
| V01 | 강한 감칠맛과 음식 전체 호감을 감칠맛 선호로 합치지 않음 | 통과 |
| V02 | 싫지 않음을 명시적 호감·혐오로 단정하지 않음 | 통과 |
| V03 | 친구의 평가를 사용자 취향으로 합치지 않음 | 통과 |
| V04 | 음식 이름에서 사용자가 느낀 감각을 생성하지 않음 | 통과 |
| V05 | 소스의 호감과 튀김옷의 아쉬움을 각각 보존 | 통과 |
| V06 | 식사 초반과 나중을 구분하고 첫입으로 좁히지 않음 | 통과 |
| V07 | 한 식사의 세 접시를 반복 식사로 세지 않음 | 통과 |
| V08–V09 | 같은 로맨틱·로스터 조합에서 구운 향과 구수함의 근거를 구분 | 통과 |
| V10 | 강도 보고가 충돌할 때 강렬형 선정을 유보 | 통과 |
| V11 | 안 달아서 좋았다는 조건을 단맛 자체의 호감으로 확장하지 않음 | 통과 |
| V12 | 미해석 조합에서 개별 감각의 호감을 만들지 않음 | 통과 |

기존 엔진 검사 16개와 평가기 검사 3개, 합계 **19개 검사 통과**를 확인했다. 평가기 검사는 빈 출력, 잘못된 부위·시점, 근거 없는 호감·타입, 네트워크 호출을 실패로 잡는지도 확인한다. 시나리오 수와 테스트 수는 서로 다른 단위다.

## 개인별 설명 비교

두 가상 사용자 모두 메인은 로맨틱, 날개는 로스터다. V08은 타르트·비스킷의 **구운 향**, V09는 곡물 푸딩·음료의 **구수함**을 좋아한다고 기록했다.

- V08 근거 요약: “가상 비스킷, 가상 타르트의 기록에 구운 향에 대한 호감이 반복돼요.”
- V09 근거 요약: “가상 곡물 음료, 가상 곡물 푸딩의 기록에 구수함에 대한 호감이 반복돼요.”

이는 모델이 작성한 문장이 아니라 현재 엔진의 근거 요약이다. 타입 이름이 같다는 이유로 같은 내용만 제공하지 않는다는 것을 검사했다. 자유로운 모델 서술의 자연스러움까지 입증하지는 않는다.

## 통과의 의미와 남은 검증

실제 API 호출은 **0회**다. V12의 기록 2개는 조합 문맥 해석이 필요해 미확정으로 남았다. 이 사례의 통과는 유보·금지 추론 방지 조건을 지켰다는 뜻이며, 조합 의미를 모두 추출했다는 뜻이 아니다.

이 자료는 현재 구현을 알고 작성한 공개 수작업 사례다. 구현 결과로 기대값을 자동 생성하지 않았지만, 미공개 홀드아웃 또는 실사용자 평가도 아니다. 이 결과에서 정밀도·분류 정확도·취향 적합성 비율을 계산하지 않는다. 결과의 `fixtureHash`는 사용한 사례를 식별한다.

각 사례에는 원문, 기대 조건, 관찰, 타입, 근거 요약, 모델 서술에 제공할 자료와 검토 초점이 들어 있다. `manualReview`의 의미 충실성·유용성·자연스러움·범위 준수 항목은 아직 `null`이다. 자동 검사의 통과를 사람의 품질 평가로 채워 넣지 않는다.

API 연결 후에는 실제 모델 출력으로 인용·부위·시점·호감·조합 의미를 확인하고, 문장의 의미와 유용성을 별도로 검토해야 한다. 인용 ID가 맞아도 그 문장이 인과나 비교를 새로 만들어낼 수 있다. 현재 모델 서술의 `model_draft` 상태를 유지하며 자동으로 확정 근거에 넣지 않는다. 메인·날개가 실제 사용자에게 맞는지는 별도의 실사용 평가 대상이다.

이번 변경은 평가 스크립트와 문서이며 앱 코드는 변경하지 않아 웹·iOS 빌드는 생략했다.
