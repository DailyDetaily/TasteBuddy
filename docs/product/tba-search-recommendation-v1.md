# TBA 검색 추천 칩 v1 — iOS 구현 계약

작성일: 2026-10-04. 적용 범위는 iOS의 기존 통합 검색창 → 추천 칩 → 기존 검색 결과 목록이다. 추천 조건은 검색 데이터에 적용하며 별도의 추천 결과 화면을 만들지 않는다. 웹·Android, 서버 학습, 운영 배포는 이번 변경에 포함하지 않는다.

## 제품 동작

- 새로운 메뉴 탐색을 중심으로 하고 저장한 식당의 재발견을 보조한다.
- 확인된 개인 취향과 메뉴 설명의 조건이 맞으면 감각 + 음식 종류를 표시한다.
- 개인 근거가 부족하면 음식 종류로 탐색하게 하고 개인 호감을 주장하지 않는다.
- 최대 4개를 표시하며 같은 메뉴 집합으로 이어지는 칩을 중복 노출하지 않는다. 개수를 채우기 위한 예시 메뉴를 생성하지 않는다.
- 칩은 문자열 검색어가 아니라 `HomeSearchRecommendationIntent`다. 표시 문구를 외부 장소·버디 검색이나 최근 검색에 자동 전송·저장하지 않는다.
- 추천 결과는 기존 `HomeSearchResultSection`의 메뉴·레스토랑 구분과 `SearchResultRow`를 그대로 사용한다. 전용 설명 영역, 메뉴 카드, `공식 메뉴`·`식당 찾기` 버튼을 추가하지 않는다.
- 메뉴 결과 항목을 선택하면 추천 의도를 해제하고 식당 이름으로 기존 검색을 실행한다. 브랜드 메뉴만으로 지점 식사 기록이나 저장을 만들지 않고, 식당을 찾은 다음 기존 기록·저장 동작을 사용한다. 장소 검색 결과를 감각 조건을 검증한 메뉴 결과처럼 합치지 않는다.

## 기존 TBA와의 매핑

| 기존 값 | 추천에서의 역할 |
|---|---|
| `SensoryAnalysisSnapshot.personalModel` | 현재 기기에서 계산한 개인 모델을 읽는다. 원문을 추천 엔진에서 다시 해석하지 않는다. |
| `PersonalTasteModelBuilder.predict` | 기존 반복·반례·중립·식사 중복·안정성 정책으로 조건별 방향을 조회한다. 별도의 2식사/수축 점수로 취향 상태를 만들지 않는다. |
| `observed_condition_direction` + `repeated_direction` | 개인 근거를 설명할 수 있는 후보의 출발 조건. 메뉴의 알려진 범위와 추가 대조한다. |
| 직접 `positive / neutral / negative` | 직접 평가 의미를 그대로 유지한다. |
| `mixed` | 원본 응답으로 다시 쓰지 않는 집계 상태. 새로운 입력 응답 종류를 추가하지 않는다. |
| `selectionEvidence` | 원래 관찰과 정의·선택 연결을 보존한다. 다른 `selectionInstanceID`의 강도를 호감에 결합하지 않는다. |
| `evidenceIDs`, `mealID` | 설명에 사용한 근거와 식사 수. 전체 식사 수 대신 해당 방향을 지지한 식사 수를 쓴다. |
| `memoryGeneration` | 기록 수정·삭제에 따른 이전 선택 무효화. |
| `memoryAccountGeneration` | 같은 로컬 모델 소유자 문자열을 쓰더라도 계정 세대를 구분한다. 다른 계정의 선택·응답을 재사용하지 않는다. |
| `sensoryAnalysisIsUpdating / sensoryAnalysisError` | 분석 중이거나 실패했을 때 개인화를 사용하지 않는다. |

추천 계층은 원본, 선택, 개인 모델에 쓰지 않는다. `profileUserID`는 기존 로컬 분석 계약의 `local-owner`를 사용하고, 계정 격리는 별도의 실제 계정 세대 UUID와 함께 확인한다. 서버 인증 주체를 이 문자열로 대체하지 않는다.

기존 TBA에서 넓은 후보가 긍정이어도 관련 원본 단위에 알려진 강도·부위·시점·다른 음식 종류가 있으면 메뉴 설명에도 그 조건이 있어야 한다. 예를 들어 강한 매운맛만 좋게 기록한 근거를 강도를 모르는 메뉴의 호감 근거로 확대하지 않는다. 새우/해산물 조건에서 얻은 호감을 야채 완탕에 확대하지 않는다. 자료가 부족하면 일반 탐색으로 남긴다.

## 첫 메뉴와 출처

첫 음식군은 `dumpling`, 감각은 `trigeminal.spicy`, 부위는 `sauce`다. 공식 페이지의 메뉴명과 설명에서 직접 확인한 두 메뉴만 포함한다.

| 메뉴 | 명시된 감각 | 알려지지 않은 값 |
|---|---|---|
| 딘타이펑 매운새우완탕 | 매운 소스 | 매운 강도, 경험 시점, 지점별 현재 판매 여부 |
| 딘타이펑 매운야채완탕 | 매운 소스 | 매운 강도, 경험 시점, 지점별 현재 판매 여부 |

출처: [딘타이펑 공식 완탕 메뉴](https://www.dintaifung.co.kr/menu/220110/wonton.php). 공개 페이지 수집 시각: 2026-10-04 12:02:57 UTC. 이 메뉴는 브랜드 공통 메뉴 정보이며 개별 지점의 판매를 확인한 결과가 아니다. 야채완탕을 채식 메뉴로 분류하지 않는다.

현재 `RestaurantCatalog`의 예시 감각 설명이나 기존 intake CSV의 추정 감각·벡터를 이 목록의 출처로 사용하지 않는다. 메뉴 데이터 수집과 앱의 추천용 읽기 모델을 구분한다.

수집과 intake 생성은 기존 파이프라인을 사용했다.

```sh
node scripts/fetch-public-restaurant-sources.mjs dintaifung-korea \
  --config tmp/public-sources/tba-search-chips-20261004/targets.json \
  --out-dir tmp/public-sources/tba-search-chips-20261004/dintaifung-korea
node scripts/bootstrap-public-source-review.mjs \
  tmp/public-sources/tba-search-chips-20261004/dintaifung-korea/manifest.json
node scripts/generate-catchtable-intake-csv.mjs \
  tmp/public-sources/tba-search-chips-20261004/dintaifung-korea/review-template.source-checked.json \
  --output-dir docs/content/intake
```

- 생성된 intake: `docs/content/intake/mvp-content-intake-dintaifung-korea-wonton.csv`.
- 앱 읽기 모델: `ios/TasteBuddy/Resources/TBA/search-recommendation-catalog.json`.
- 소스 문구는 직접 대조했다. 사람의 실식 평가·맛 벡터 검수를 수행했다고 표기하지 않는다.
- 추정 맛 벡터, 온도, 강도는 생성하지 않았다. Supabase seed 생성·가져오기와 운영 DB 쓰기는 수행하지 않았다.
- `reviewAfter`는 수집 30일 뒤의 내부 재확인 기한이다. 실제 판매 종료일이 아니다. 기한이 지나면 해당 메뉴는 추천에서 빠진다. 다음 출처 확인 때 날짜와 revision을 함께 갱신해야 한다.

## 추천과 실행

1. 지원하는 카탈로그 버전, 출처 URL, 확인·재검토 시각, 중복 ID를 검사한다.
2. 공식 메뉴의 음식군과 명시된 감각으로 후보를 만든다.
3. 개인 모델의 같은 음식군·감각·부위 조건을 조회한다. 강도·시점의 불일치나 누락은 개인 호감으로 확장하지 않는다.
4. 확인된 동일 조건의 불호는 해당 메뉴의 선제 추천에서 제외한다. 정보 부족을 감각 부재로 바꾸지 않는다.
5. 개인 취향 연결 → 저장 재발견 → 일반 탐색의 순서로 정렬한다. 메뉴 집합 Jaccard 0.7 이상인 중복 칩을 제거한다. 순서는 결정론적이다.
6. 한 메뉴만 남으면 그 메뉴명을 표시한다. 그룹형 표현으로 여러 선택지가 있는 것처럼 보여주지 않는다.
7. 선택은 계정·근거 세대, 정책 버전, 조건, 근거 ID, 후보 ID와 5분 만료 시각을 가진다.
8. 실행 시 현재 메뉴 자료로 음식군과 감각 조건을 다시 확인한다. 해당 선택의 후보 ID 밖의 메뉴를 자동 추가하지 않는다. 메뉴 revision이 바뀌면 이전 개인 근거를 새 레시피에 자동 승계하지 않고 그 결과를 제외한다. 결과가 줄거나 0개가 되어도 조건을 완화하지 않는다.

메뉴 링크의 유효성, 출처가 주장한 특징, 개인 취향 근거는 서로 다른 정보다. 내부 순위와 근거 수를 만족 확률로 표시하지 않는다. 선정 과정이 TBA 관찰을 추가하거나 클릭을 호감으로 저장하지 않는다.

## 갱신과 외부 검색 경계

- 선택된 추천이 있을 때는 기존 외부 장소·공개 프로필 검색 작업을 실행하지 않는다.
- 사용자가 검색어를 수정하면 구조화된 선택과 이전 이유를 해제한다.
- 기록 세대, 계정 세대, 분석 준비 상태가 바뀌면 선택·문구·진행 중 검색을 정리한다.
- 선택 만료와 앱 재활성화 때 유효성을 확인한다. 5분 만료는 로컬 선택의 유효기간이며 다른 기기의 변경을 실시간 확인하는 기능이 아니다.
- 저장한 식당 결과는 실행 시 현재 저장 목록과 다시 대조한다.
- 결과 항목을 선택했을 때만 식당 검색으로 이어지며 외부로 전달하는 값은 식당 이름이다. 원문·근거 ID·추천 이유는 포함하지 않는다.

## 검증 범위

`HomeSearchRecommendationTests`는 기존 TBA의 실제 모델과 분석기를 사용해 반복 근거, 같은 식사 중복, 반례, 조건 누락, 다른 선택의 강도, 계정/근거 변경, 만료, 메뉴 출처 변경, 저장 해제와 결과 중복을 검사한다.

`HomeSearchRecommendationUITests`는 `--search-recommendation-qa`의 별도 preview 저장소에서 합성 원문 3개로 추천 → 기존 검색 결과 → 근거 1개 삭제 → 일반 탐색 전환을 확인한다. `--search-recommendation-empty`는 기록 없는 상태를 검사한다. 근거 삭제·외부 검색 호출 수 컨트롤은 `--search-recommendation-controls`를 추가할 때만 표시한다. 화면 캡처는 이 컨트롤을 제외한 실제 검색 컴포넌트에서 얻는다. 이 가상 기록은 실제 계정에 저장하지 않는다.

검사 실행 결과는 `output/qa/tba-search-chips-20261004/`에 남긴다. 앱 빌드, XCTest, UI 실행 여부와 실제 사용자 추천 품질은 따로 보고한다.

전용 결과 화면 제거 전의 2026-10-04 검사 기록: 앱·테스트 번들 빌드 성공, 1차 회귀 52개 통과, 조건·메뉴 버전 보강 후 추천·검색 32개 통과, 시뮬레이터 UI 2개 통과. 해당 화면 캡처는 현재 UI를 나타내지 않는다. 실기기·실제 사용자 추천 만족도·운영 배포를 검증한 결과는 아니다.

전용 결과 화면 제거 후 실제 실행: 추천·기존 검색 단위 검사 34개 통과, 시뮬레이터 UI 2개 통과. 기존 검색의 결과 개수·메뉴 구분·목록 행을 사용하고 전용 추천 설명·버튼이 나타나지 않는지 확인했다. 메뉴 행 선택 → 공개 식당 이름 검색과 취향 근거 삭제 → 일반 탐색 갱신도 확인했다. 첫 화면 검사 시도는 실행 준비 지연으로 중단했고, 생성된 앱·검사 번들을 재사용해 재실행했다. 결과 번들에서 34/34 및 2/2 통과를 확인했으며 현재 화면은 `existing-search-chips.png`, `existing-search-results.png`다.

## 이후 범위

이번 v1은 첫 조건의 완결 경로다. 지역·가격·식이 제외 필터, 노출 이벤트의 영속 수집·반복 피로 조정, 인접 취향 전이, 학습형 정렬, 만족 확률, 웹·Android 적용은 추가 설계·데이터가 필요한 후속 범위다. 현재 없는 필터를 적용했다고 표시하지 않는다. 새로운 감각이나 음식군을 추가할 때는 그 범위의 메뉴별 출처와 UI 설명을 함께 확장한다.
