# TBA 감각 모델과 네이티브 앱 연결

작성일: 2026-09-06 · JS `tba-personal-engine/2`, 정제 `tba-rules/4`, Swift `tba-native-sensory/1`

개인 취향의 의미를 먼저 이해하는 제품 방향에 맞춰 감각 상세를 구조화하고 네이티브 앱의 해석 경로를 교체했다. API 연결은 사용자 요청에 따라 보류했다. **앱 연결과 구조·계약 검증은 자연어 의미 해석 품질의 완성과 다르다.** 미등록 표현과 복잡한 관계를 정확히 해석하는 품질은 추가 검증이 필요하다.

이후 주 입력을 미각 버블·디테일 태그의 구조화 선택으로 확장했다. 당시 라벨과 감각별 직접 평가·조건을 보존하며 메모 없이 해석할 수 있도록 연결한다. 아래 앱 전환 검증은 해당 시점의 이력이며, 선택형 입력의 변경과 최신 검증은 [선택형 수집 현황](./tba-structured-selection-intake.md)에서 별도로 기록한다.

## 감각을 정리하는 범위

미각, 향, 식감, 입안감각, 온도, 자극, 여운의 구체적 표현을 원문과 함께 보존한다. 감각의 존재, 느낀 강도, 직접 호감·아쉬움, 알맞다고 느낀 수준, 부위와 시점, 조합을 분리한다. 음식 이름이나 강도·전체 평가로 특정 감각의 호감을 채우지 않는다. 비유 속 향은 실제 재료의 존재로 변환하지 않는다.

- `sensory_detail`은 정확한 원문을 값으로 갖는다. 알려진 감각의 묘사와 `aroma.unspecified` 같은 미분류 묘사를 구분한다.
- `겉은 가볍게 부서지고 속은 촉촉했다`는 겉과 속의 묘사를 따로 남긴다. 호감은 쓰지 않았으므로 만들지 않는다.
- `버터 같은 향은 좋았지만 입안에 남는 기름진 느낌은 아쉬웠다`는 향의 비유·호감과 남는 감각·아쉬움을 따로 다룬다.
- `단맛이 없어서 좋았다`는 단맛 자체의 호감으로 일반화하지 않는다. 부재 조건을 함께 유지한다.
- `향이 종이처럼 납작해서 좋았다`, 복잡한 온도 변화·대명사·조건 비교처럼 의미를 확정할 수 없는 문장은 원문과 미해석 사유를 남긴다. 원문 저장을 의미 해석 성공으로 세지 않는다.
- 식당 조명·직원 말투·분석 요청·타인의 경험을 음식에 대한 본인의 감각으로 바꾸지 않는다.

[상세 해석 모듈](../../scripts/tba-engine/sensory-understanding.mjs)은 감각별 구조, 범위별 직접 평가, 강도와 호감이 함께 보고된 조건, 부위·시점의 평가 차이, 선택 확인 후보를 생성한다. 같은 범위에 상충한 강도 보고가 있으면 강도와 호감의 관계를 단정하지 않는다. 원인·최적 강도·인구집단 확률은 만들지 않는다. 좋은 미식 경험 전반의 환경·서비스·동행은 부가 맥락이며 감각 분석의 주제를 대체하지 않는다.

## 앱에서 교체한 경로

| 화면·구성 | 현재 데이터와 동작 |
| --- | --- |
| 홈 인사이트 요약 | 동일 `sensoryAnalysis`의 현재 해석·직접 근거 기록·인사이트를 기존 카드 구조로 표시한다. 고정 기간별 취향 변화는 생성하지 않는다. |
| 나의 입맛 | 실제 기록의 메인·윙 후보, 반복·조건·강도·시점·부위별 해석과 원문 근거를 연결한다. 빈 기록·계산 중·실패·미해석 상태를 구분한다. |
| 다이닝 카드 | 같은 기록 ID의 새 관찰·인사이트만 사용한다. 강도 평점·과거 분석 캐시에서 감각 태그나 호감을 만들지 않는다. |
| 프로필·입맛 현황 | 실제 정제 기록과 인사이트 수를 사용한다. 설문 축을 현재 취향의 색상 벡터나 확신 점수로 사용하지 않는다. |
| 변화 화면 | 실제 기록에서 명시한 시점·부위·조건의 차이를 표시한다. 샘플 점수·고정 날짜·가짜 장기 변화 차트를 제거한다. |
| 식당·메뉴 상세 | 새 모델에서 계산하지 않은 개인 Fit·신뢰도·유사 집단 신호·과거 식사 비교는 미계산 상태다. 제목·설명·메뉴 정보는 보존한다. |
| 검색·공개 프로필 | 실제 검색 실패를 샘플 친구 결과로 덮지 않는다. 연결되지 않은 관계·활동 통계는 미제공으로 표시한다. |
| 기존 설문 결과 | 입력과 기존 응답 저장을 보존하되 설문 참고값으로 설명한다. 이 값이 새 모델의 확정 취향·호감·실험적 강도를 뜻하지 않는다. |

`AppModel`은 시작 시 저장된 원문을 새 엔진으로 읽는다. 기록 저장·수정·삭제 때 이전 화면 결과를 즉시 비우고 비동기로 재계산한다. 계산 시작 버전을 비교하여 늦게 끝난 과거 결과를 적용하지 않는다. 미완료 캡처는 취향 근거에 포함하지 않는다.

원문 `DiningEntry`, 명시 선택, 사진을 일괄 삭제하거나 다른 내용으로 덮어쓰지 않는다. 기존 디스크의 TBA 이벤트·confidence·분석 캐시는 현재 계산에서 제외하며 새 기록에는 구 분석 스냅샷을 만들지 않는다. 기존 원문을 읽어 새 해석을 만드는 전환이다. 테스트·과거 호환 코드와 원본 음식 자료가 저장소에 남아 있다고 현재 앱이 그 분석을 사용하는 것은 아니다.

## 공유 계약과 집계

[계약 생성기](../../scripts/build-tba-sensory-native-contract.mjs)는 정제 규칙의 데이터, 845개 어휘, 정제 135개 예문, 메인·윙 15개 예문을 [리소스 JSON](../../ios/TasteBuddy/Resources/TBA/tba-sensory-contract.json)으로 내보낸다. Swift는 앱 내부 구현이며 JavaScript를 앱에서 실행하거나 가져오지 않는다. 양쪽 정제 결과의 값·원문 UTF-16 위치·대상·시점·미해석 상태와 대표 타입 계약을 비교한다.

네이티브의 `DiningEntry`에는 같은 식사를 묶는 `mealId`가 없다. 따라서 `completedExperienceCount`, `sourceExperienceCount`는 **저장 기록 ID별 개수**다. 앱은 이를 식사 횟수나 독립 표본 수로 표시하지 않는다. `sourceExperienceCount`는 미분류 묘사만 있는 기록을 제외하며, 미해석 기록 수는 별도로 다룬다. JS 저장소에서 명시적으로 제공하는 `mealId`와 동일한 집계라고 주장하지 않는다.

메인·윙은 직접 평가의 반복을 정리하는 임시 표시 정책이다. 검증된 성격 유형이나 분류 확률이 아니다. 서로 다른 평가가 동률이면 유보하며 같은 관찰을 두 타입의 별도 근거로 중복 사용하지 않는다. 같은 식사의 접시를 정확히 묶는 기능은 후속 데이터 계약이 필요하다.

## 실제 검증

- Node 통합 검사 99개와 감각 구조·관계·수정·삭제 추가 검사 3개, 합계 102개가 통과했다.
- 생성 계약 검사와 기존 120개 의미 회귀 검사를 통과했다. 이 회귀 결과를 실제 사용자 자연어 정확도로 해석하지 않는다.
- Swift 정제 135개와 메인·윙 15개 예문 비교를 통과했다. iOS 시뮬레이터 앱·테스트 빌드도 성공했다.
- 전체 XCTest 실행에서 184개 중 183개가 통과했고, 나머지 1개를 수정한 뒤 한정 재실행에서 통과했다. `testAnalysisMainScrollDoesNotOverflowHorizontally`의 실패 원인은 검사에서 헤더·하단 inset을 세로 스크롤 가능 범위에 포함하지 않은 것이었다. 실제 크기로 이 원인을 확인한 뒤 범위 계산을 수정했으며, 콘텐츠를 직접 이동하는 검사도 통과했다. 최종 전체 184개를 한 번에 다시 실행한 결과는 아니다.
- 전용 iPhone 17 Pro 시뮬레이터에서 가상 기록으로 홈과 나의 입맛 화면을 실행하고 캡처를 확인했다. 홈 요약 카드의 메인·윙 이름 잘림을 수정한 후 표시를 다시 확인했다. 실제 기기·실제 사용자 기록·터치 상호작용 전체 검증은 수행하지 않았다.
- 실제 LLM/API 호출은 0회다. 원문과 모델 후보의 구분, 미해석 상태를 유지하며 운영 API 연결은 하지 않았다.

별도 수작업 개발 검토 문장 50개에서 상세 표현 회수는 16/42, 명확한 호감 회수는 7/15, 미해석 포함은 39/50이다. 선택한 자동 안전성 제약 위반과 잘못된 원문 위치는 0건이지만, 모든 의미·대상·관계의 정확성을 보증하지 않는다. 수정 피드백에 사용한 공개 개발 세트이며 비공개 최종 평가가 아니다. [평가 근거와 공개 자료](./tba-sensory-reference-notes.md), [실행 결과](./tba-sensory-review-results.json)를 함께 본다.

이 수치로 프리미엄 서비스의 해석 품질이 완성됐다고 판단할 수 없다. 풍부한 자연어를 해석하는 API 연결과 실제 동의한 기록의 관계·의미 평가, 사용자 이해·유용성 검토가 남아 있다. 외부 감각 자료는 개념 검토에 사용하며 개인 취향 근거로 합치지 않았다.

## 실행과 후속 작업

```sh
node --test scripts/tba-platform-pilot/*.test.mjs scripts/tba-engine/*.test.mjs
node scripts/build-tba-sensory-native-contract.mjs --check
node scripts/tba-engine/sensory-review-evaluation.mjs --output docs/product/tba-sensory-review-results.json
```

iOS는 XcodeGen 프로젝트를 생성하고 `TasteBuddy` scheme을 iOS 시뮬레이터에서 빌드·테스트한다. DEBUG 또는 시뮬레이터 빌드 전용 `--sensory-home-qa`, `--sensory-analysis-qa`는 별도 UserDefaults의 가상 기록으로 실제 화면을 확인한다. 사용자 계정 기록은 바꾸지 않는다.

사용자가 요청한 **온보딩 설문 재설계**는 후속 단계로 둔다. 새 모델이 필요한 감각·호감·조건을 적은 부담으로 수집하고 첫 식사 기록으로 이어지게 한다. 선언한 일반 취향과 실제 먹은 경험을 서로 다른 근거 종류로 저장하며, 미경험·모름·건너뛰기를 중립 평가와 구분한다. 시작부터 아홉 타입이나 확신 수치를 강제하지 않는다. 이번 연결 작업에서 설문 문항을 새로 설계하지 않았다.

운영 서버의 분석 저장·동기화와 계정별 데이터 범위, 조건부 AI의 실제 의미 품질, 식사 묶음, 그룹·추천은 각각 별도 검증이 필요한 후속 작업이다.
