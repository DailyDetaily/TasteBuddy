# TBA 추론 기준 감사 프롬프트

작성일: 2026-10-02. 목적: 이 프롬프트를 실제 소스에 적용하고, 질문·답변·반례·판정 근거가 있는 감사 결과를 만든다.

## 실행 프롬프트

너는 TBA의 독립 추론 감사자다. 현재 체크아웃의 입력 → 관찰 → 식사 단위 근거 → 개인 취향 가설 → 질문 → 사용자 문장 경로를 추적하라. 파일 이름이나 설계 문서를 현재 실행 동작의 증거로 대신하지 마라. 현재 앱 진입점과 호출 관계를 먼저 확인하라.

감사의 목적은 사용자의 적은 기록으로 무엇을 말할 수 있는지, 무엇은 더 확인해야 하는지, 무엇을 말하면 근거를 넘는지 판정하는 것이다. 정해진 결함 개수를 채우거나 모델 교체를 미리 결론내리지 마라.

### 작업 범위

- 기준은 현재 working tree다. 기존 미커밋 변경을 보존한다. 제품 코드·설정·사용자 데이터는 수정하지 않는다.
- 감사 프롬프트·보고서·합성 재현 코드·실행 결과만 별도 경로에 작성한다.
- iOS 실제 분석 경로를 우선 확인하고, 웹·공유 JS·Android는 확인한 범위만 명시한다. 레거시·설계안·현재 제품·테스트 전용 경로를 구별한다.
- 도구로 실행한 결과와 소스만 읽은 판단을 분리한다. Mac의 JS/Swift 검증을 시뮬레이터·실기기·운영 검증으로 확대하지 않는다.
- 합성 기록은 합성이라고 명시하고 실제 사용자 관찰이나 정확도 근거로 저장하지 않는다.
- 문서의 과거 통과 수를 현재 통과 수로 재사용하지 않는다. 자연어 품질·사용자 효용은 실제 평가가 없으면 미검증으로 남긴다.

### 스스로 답할 질문

1. **현재 경로:** 실제 앱이 읽는 원본, 파서, 개인 모델, 표시 계층은 무엇인가? 같은 이름의 구 엔진이 현재 결과에 관여하는가?
2. **관찰의 의미:** 감각의 존재·강도·호감·알맞음·음식 전체 평가·재선택 의향·미응답·부재가 끝까지 구별되는가?
3. **출처와 연결:** 다른 사람·음식·선택·부위·시점의 응답이 합쳐지지 않는가? 음식 지식·사진·생성 요약을 사용자 관찰로 승격하는 경로가 있는가?
4. **독립 근거:** 같은 식사의 여러 접시, 중복 입력, 여러 태그, 재분석을 반복 경험으로 세지 않는가? 식사 식별자가 없을 때의 대체가 어떤 주장을 허용하는가?
5. **판단 문턱:** 최소 식사 수·다수결·한 식사 제거 안정성·조건 차원 제한은 무엇인가? 구현상 정책과 경험적으로 검증된 기준을 구별하는가?
6. **반례와 유보:** 반대 기록·중립·동률·식사 내 충돌·새 조건에서 무엇을 보류하는가? 조건부 설명까지 불필요하게 차단하거나 일반 결론으로 우회하는가?
7. **조건과 변화:** 강도·음식·부위·시점이 함께 달라질 때 한 조건의 효과를 단정하는가? 기간 변화와 먹은 음식 구성 변화, 당시 알려진 정보와 나중 정정을 구별하는가?
8. **질문 정책:** 다음 질문은 무엇을 최적화하는가? 해석 개수·질문 난이도·기억의 정확성·응답 부담·중복 질문·묻지 않을 선택은 어떻게 반영되는가?
9. **수정과 삭제:** 원문 수정·삭제·선택 해제 후 관찰·가설·질문·화면이 함께 무효화되는가? 오래된 비동기 결과가 복원될 수 있는가?
10. **최종 주장:** 화면의 유형명·요약·변화 문장이 내부 근거보다 넓은 정체성·원인·확률을 말하는가? 관찰 사실과 다음 경험 예측이 명확한가?
11. **평가의 타당성:** 정답 생성, 개발/평가 분리, 사용자/식사/시간 분리, 관계 해석, 오류와 유보가 평가되는가? 테스트 통과로 주장할 수 없는 품질은 무엇인가?
12. **우선순위:** 실제로 고쳐야 할 결함, 의도된 정책의 한계, 실자료가 필요한 연구 질문을 나누면 무엇을 먼저 해야 하는가?

### 판단 계약

각 질문에 `관측 사실`, `현재 허용되는 해석`, `금지되는 확대 해석`, `추가 근거`, `출처 또는 재현 결과`를 답하라. 확정할 수 없으면 왜 확정할 수 없는지 적어라.

각 발견은 다음 중 하나로 분류한다.

| 분류 | 요건 |
| --- | --- |
| 재현된 결함 | 명시된 계약과 다른 결과를 현재 코드에서 실행 재현 |
| 소스로 확인된 불일치 | 실제 연결된 경로의 서로 다른 기준/문장 확인, 앱 실행 검증 여부 별도 |
| 정책의 한계 | 현재 정책대로 동작하지만 표현력·효용·조건 범위가 제한됨 |
| 평가 공백 | 해당 품질을 판정할 독립 평가가 없음 또는 현재 평가가 검사하지 않음 |
| 보장된 경계 | 확인한 사례와 코드 범위에서 금지 추론을 차단함 |

심각도는 사용자에게 잘못된 취향을 제시하거나 유효 근거를 잃는 영향, 실제 도달 경로, 반복 가능성으로 정하라. 확신도와 심각도를 혼동하지 마라. 반례 하나에서 전체 정확도를 추정하지 마라.

### 반례 묶음

예상 결과를 먼저 적고 현재 결과를 비교한다. 구현의 결과를 그대로 정답으로 복사하지 않는다.

- 강도만 있음 / 호감만 있음 / 알맞음만 있음 / 전체 평가만 있음.
- 같은 식사 3접시와 서로 다른 식사 3회.
- 같은 관찰 중복과 식별자는 같지만 내용이 다른 관찰.
- 긍정 3회, 긍정 3회+부정 1회, 긍정 3회+중립 1회, 동률.
- 약한 산미 긍정 반복 + 강한 산미 부정 반복; 강도와 음식 종류가 동시에 바뀌는 사례.
- 서로 다른 선택의 강도·호감과 검증된 부모-디테일 연결.
- 감각 부재에 대한 호감, 비유, 대명사, 식사 내 시간 변화, 타인의 평가.
- 알려지지 않은 조건으로 예측 요청, 수정 전 시점 조회, 수정·삭제 후 결과.
- 질문에 임시 적용한 가상 답변이 관찰이나 근거 수로 새어 들어가지 않는지.

### 독립 반박 단계

초기 발견마다 반대 입장에서 검토하라: 이 코드는 현재 경로인가? 입력이 실제 허용되는가? 이미 다른 계층이 차단하는가? 넓은 이름 아래 표시해도 본문이 범위를 제한하는가? 단지 보수적 정책을 버그라 부르고 있지 않은가? 이 테스트가 구현 자체를 정답으로 삼고 있지 않은가?

반박으로 약해진 발견은 등급을 낮추거나 제외하고, 이유를 보고서에 남긴다. 하나의 에이전트가 주장하고 다른 에이전트가 동의했다는 사실만으로 검증됐다고 하지 않는다.

### 최종 산출물

1. 범위, 소스 기준 시점, 실행 환경과 검증 한계.
2. 위 12개 질문에 대한 직접 답변과 소스 위치.
3. 핵심 발견: 입력 → 실제 결과 → 왜 문제/한계인가 → 허용 문장 → 완료 기준.
4. 반례 실행 표와 재실행 가능한 합성 probe, 원본 로그/결과.
5. 이미 작동하는 보호 규칙과 독립 반박 후 제외한 주장.
6. `현재 말할 수 있음 / 추가 근거 필요 / 말하면 안 됨` 판단표.
7. 우선 작업 3개와 실자료 평가 설계. 관찰하지 않은 실제 사용자 정확도는 숫자로 만들지 않는다.

이제 사용자에게 질문을 되돌리지 말고, 위 질문에 스스로 근거를 모아 답하여 감사를 끝내라.
