# 선택형 감각 입력 독립 개발 평가

이 시나리오는 생산 선택 정제 코드나 실행 결과를 읽기 전에 현재 앱의 `dining-feedback-scenario.json`에 있는 72개 미각 버블과 60개 디테일 태그의 라벨을 직접 확인하고 작성했다. 실제 사용자 데이터가 아닌 수작업 개발 평가다. 실패를 구현 담당자에게 전달하면 비공개 holdout으로 부르지 않는다. 실제 모델/API 호출은 하지 않는다.

## 필수 계약과 아직 확인할 사항

고정 선택 ID와 종류, 카탈로그 버전, 당시 라벨, 감각별 직접 호감·강도·적정수준, 대상·시점, 선택 간 연결을 각각 보존해야 한다. sourceField는 실제 선택 ID와 facet을 포함해야 한다. 추천 목록은 후보이며 저장된 선택 목록과 구분한다. nil은 legacy 호환, 빈 목록은 명시적 해제로 다르게 취급한다.

`bitter`와 `fat` 등의 화면 분류 축이나 버블의 배치용 숫자를 감각 의미/호감으로 읽으면 안 된다. 자동 생성 메모와 사용자가 직접 쓴 문장을 구분할 출처가 필요하며, 선택을 문장으로 펼쳐 다시 읽은 것은 새 근거가 아니다. 빈 메모에서도 선택과 직접 평가가 충분하면 해석이 가능해야 한다.

확인 범위는 선택 계약·출처·평가 분리·수정/삭제·호환 복원이다. 전체 언어 이해 정확도, 실제 사용자 취향 예측 정확도, 새 카탈로그의 완전한 심리측정 타당도를 주장하지 않는다.

## 현재 입력 UI 점검

초기 점검에서는 문장 입력이 완료 조건은 아니었다. 저장 함수는 미각 버블 하나를 요구하지만 메모를 요구하지 않았다. 다만 빈 메모를 `메인 미각 …으로 기억에 남은 식후 피드백입니다.` 형태의 자동 요약으로 채웠다. 이 자동 문장을 다시 감각 증거로 읽지 않도록, 새 입력의 메모는 비어 있을 수 있게 하고 예전 자동 요약은 출처가 다른 기록으로 구분해야 한다.

추천 태그 목록과 실제 선택 ID 목록은 별개였다. 선택 UI가 직접 호감·강도·알맞음을 수집할 때도 이 구분을 유지해야 한다. `구운 향`이 쓴맛 영역에 배치된 사실, 버블 지도에 배치하기 위한 숫자는 사용자가 보고한 쓴맛·강도가 아니다. `균형이 좋음`, `굽기가 좋음` 같은 복합 태그는 그 표현 자체의 직접 평가를 보존하되 특정 기본 맛의 호감으로 펼치지 않는다.

## 구현 계약 연결 및 검증 범위

- `SensoryStructuredSelectionTests.swift`: SS-01~20을 Swift 계약에 연결했다. 별도 facet, 실제 버튼 문구, ID·버전·당시 라벨, UTF-16 원문 span, 관련 버블 연결도 검사한다.
- `AppModelStructuredSelectionPersistenceTests.swift`: 빈 메모 + 명시 선택의 전체 필드 저장·재시작, 같은 식사의 호감 정정, `[]` 해제 후 남은 legacy ID의 부활 방지를 비동기 새로고침까지 확인하는 두 검사를 추가했다.
- 상태: 동결 SS-01~20과 AppModel 저장·재시작 검사 2개는 전체 XCTest 230개 실행에 포함되어 모두 통과했다. 별도로 JS 파서에 해당하는 SS-01~07, SS-14~16, SS-19~20의 12건도 통과했다. AppModel 재생성에 따른 저장 복원 검사이며, 실제 기기의 재부팅이나 모든 화면 조작 검증을 뜻하지 않는다. 테스트 개수는 해석 정확도가 아니다.

SS-18의 실행 fixture는 식별 가능한 기존 자동 요약 형식을 사용한다. 현재 계약은 임의 자동 문장과 직접 쓴 문장을 구분하는 `noteOrigin` 필드를 포함하지 않으므로, 모든 종류의 자동 생성 문장을 탐지한다고 주장하지 않는다. 직접 메모까지 일괄 무시하는 것은 이 기대의 의미가 아니다. 명확히 확인할 수 있는 기존 자동 요약의 중복 근거 생성 방지가 현재 자동 검사의 범위다.

미지원 ID·버전·ID/라벨 충돌은 선택 원문을 보존하고 유보한다. 반면 카탈로그에 정의된 모호한 감각 표현의 직접 호감은 구조화된 선택 출처와 함께 보존할 수 있다. 이런 호감을 일반적인 감각 사실이나 메인·윙 성향 확정으로 올리는 것은 별도 판단이며, 전자를 보존했다는 이유만으로 후자까지 성공이라고 세지 않는다.

## JS 저장 연동 검증

선택 출처를 소비하는 JS 경로의 최소 연동 후 `ai-extraction.test.mjs`, `experience-evidence.test.mjs`, `insight-views.test.mjs`를 묶어 실행해 25개가 통과했다. 새 검사는 당시 라벨의 정확한 span과 선택 ID 범위, 다른 선택·facet identity의 분리, 실제 PGlite 저장과 재정렬 후 원래 evidence ID·as_of 유지, 응답 정정의 교체, 같은 ID의 상반된 DTO 유보, `[]`·clear·remove 후 관찰과 유보 제거 및 재분석 시 부활 방지를 포함한다. 실제 외부 API 호출은 0이었다.

이 결과는 UI에서 전체 선택 해제를 저장할 수 있다는 증거는 아니다. 읽기 점검 시 미각을 모두 해제하면 다음 버튼이 숨겨지고 저장 함수의 필수 미각 guard가 동작해, 기존 기록의 전체 해제 저장 경로가 없었다. 데이터 계약 검사와 화면 기능의 이 차이는 별도 UI 수정·검증이 필요하다.
