# TBA 조건부 개인 취향 모델

상태: 로컬 모델 구현·앱 연결·독립 개발 평가와 시뮬레이터 화면 검증 완료(2026-09-06). 기존 선택형 수집과 전체 5단계 평가를 입력으로 사용하며 외부 API는 보류 상태다. 이 문서의 완료 기준은 현재 제품 모델의 구현·계약·개발 평가에 대한 기준이다. 실제 사용자의 해석 만족도나 음식 선택 성공률까지 검증되었다는 뜻은 아니다.

알맞음 반복 집계, 전체 평가 교차 해석, 답변 영향에 따른 질문 선정은 [개인 모델 v2 확장](tba-personal-insights-v2.md)에 이어서 정리한다. 아래 2026-09-06 실행 결과와 동결 평가는 당시 검증 기록을 그대로 보존한다.

## 이번 모델이 해결하는 문제

같은 산미를 어떤 식사에서는 좋아하고 다른 식사에서는 아쉬워할 수 있다. 전체 평균이나 가장 많은 반응만 보여주면 이 차이가 사라진다. TBA는 직접 고른 감각 평가와 강도·부위·시점·음식 종류를 함께 비교하고, 확인된 범위와 다른 사례를 설명한다. 조건이 함께 달라졌다면 어떤 하나가 원인이라고 말하지 않는다.

전체 5단계 평가는 음식 전체에 대한 별도 응답이다. 전체가 많이 아쉬웠어도 동일한 개별 산미 응답을 더 강한 불호로 바꾸지 않는다. 강도, 알맞음, 호감은 각각 저장한 원값을 유지한다. 미응답은 중립이 아니며 추천 노출이나 질문을 넘긴 행동은 맛 평가가 아니다.

## 원자료와 반복 근거

- `DiningEntry.id`: 수정·삭제·사진·근거 조회에 사용하는 저장 레코드 식별자.
- `mealID`: 실제 같은 식사를 묶는 식별자. 한 식사의 여러 접시는 다른 레코드여도 반복 식사 한 번이다. 사용자가 같은 식사에 메뉴를 추가하는 흐름에서만 공유하며 시간이나 식당 이름으로 임의 합치지 않는다.
- `observedAt`: 기록한 경험의 시각. 현재 입력 흐름이 제공하는 시각의 범위를 넘어서 정확한 섭취 시각이라고 주장하지 않는다.
- `savedAt`, `updatedAt`: 최초 저장과 마지막 수정이 알려진 시각. 레거시에는 당시 정보가 없으므로 `nil`을 유지한다.
- `restaurantID`, `menuItemID`, `dishKindIDs`: 실제 입력이나 메뉴 경로가 제공한 음식 문맥. 이름을 가짜 안정 ID로 바꾸거나 이름에서 미선택 감각을 생성하지 않는다.

레거시의 `mealID`는 기존 `id`, `observedAt`은 기존 `date`를 사용한다. 이는 복구 규칙이지 레거시 두 레코드가 서로 다른 실제 식사라는 확인이 아니다. 과거 레코드가 실제 같은 식사였는지는 추가 자료 없이는 알 수 없다.

같은 식사·속성·명시 조건의 여러 선택과 facet은 연결된 근거다. 서로 같은 응답이면 반복 수를 늘리지 않고 출처를 합친다. 같은 범위에 반대 응답이 있으면 `mixed`로 보존한다. 이를 평균으로 중립으로 바꾸거나 오류라고 삭제하지 않는다. 동일한 문구라도 서로 다른 식사라면 각 식사의 근거를 보존한다.

## 모델의 계산과 출력

모델은 감각별 기본 응답 분포와 실제 관찰된 조건의 응답 분포를 다시 계산한다. 비교 후보는 최대 두 차원의 명시 조건으로 제한한다. 조회에서는 입력한 모든 조건을 함께 만족하는 실제 식사도 확인해 미관찰 조합을 막는다. 이는 충분한 자료 없이 복잡한 조합을 확정하는 것을 줄이는 구현 정책이며 실제 최적 모델이라는 주장이 아니다.

각 출력은 다음 정보를 가진다.

1. 무엇이 반복되거나 달라졌는지에 대한 해석과 적용 조건.
2. 호감·중립·아쉬움·동일 범위 상충을 구분한 식사 근거.
3. 해석과 다르게 나타난 식사의 원문과 선택 출처.
4. 최소 식사 수와 식사 하나를 제외했을 때 결과가 유지되는지에 따른 판단·유보 상태.
5. 이미 받은 응답을 제외하고 다음에 확인할 선택 한 가지.

반대 기록을 숨기거나 미관찰 조건에 대해 좋아할 것이라고 확정하지 않는다. 내부 분포를 계산하더라도 이를 보정된 미래 예측 확률이나 사용자에게 보여줄 정확도 점수로 표현하지 않는다. 식사 하나를 제외한 안정성은 개발용 민감도 검사이며 모집단 검증이나 인과 검증이 아니다.

질문은 감각의 호감 미응답, 비교에 필요한 조건 누락, 아직 확인하지 못한 조건을 구분한다. 동일 의미의 질문에는 결정적인 식별자를 사용한다. 노출·넘김 이력은 개인별로 보존하고 질문 반복 제어에만 쓴다. 새로운 직접 선택이 저장된 뒤에만 학습 자료가 달라진다.

기록 보완 질문은 근거가 된 기존 식사를 열어 수정한다. 탐색 질문은 새 식사를 기록하며, 제안한 강도와 직접 호감이 같은 유효 조건에 함께 있어야 완료된다. 강도만 선택하거나 다른 감각·대상·시점의 응답을 저장한 경우에는 질문을 해결했다고 처리하지 않는다. 원기록이 삭제되었거나 새 식사의 ID가 기존 기록과 충돌하면 덮어쓰지 않고 저장 실패를 안내한다. 넘긴 질문은 즉시 다른 질문으로 교체하지 않으며 다음 자연스러운 분석 갱신에서 후보 선택에서 제외한다.

## 시간 경계와 수정·삭제

현재 해석은 현재 유효한 원자료에서 매번 재계산한다. 수정한 이전 응답, 명시적으로 해제한 선택, 삭제한 기록은 근거·예외·질문에서 함께 회수한다. 감각 선택 `nil`의 레거시 복원과 명시적인 빈 배열 `[]`의 해제는 구별한다.

지정 시점의 개발 평가는 관찰 시각과 당시 알려진 시각을 모두 확인한다. 시점 이후에 저장·수정된 내용은 이전 평가 입력에 넣지 않는다. 과거 수정본을 저장하지 않은 자료는 당시 상태를 복원할 수 없으므로 현재 자료 필터를 완전한 과거 재현이라고 부르지 않는다. 레거시의 알려진 시각이 없으면 그 한계를 결과에 보존한다.

[32개 독립 평가 기준](tba-advanced-model-evaluation.md)은 새 생산 알고리즘을 읽기 전에 동결했다. 결과를 본 뒤 정답을 구현에 맞춰 바꾸지 않는다. 미연결이나 미실행을 통과로 표시하지 않는다.

합성 평가는 조건 반전·무조건 안정·무신호·희소·여러 조건의 동시 변화에서 모델을 단순 감각별 기준선과 비교한다. 평가 대상 식사 전체를 입력에서 제외하고 이전 시점의 자료만 사용한다. 정확도와 답한 비율을 함께 보고하여 많이 유보한 모델이 정확도만 높게 보이는 일을 피한다. 이 데이터는 실제 사용자 성공률을 측정하지 않는다.

## 설계 참고

5단계 범주의 간격을 같은 수치 간격으로 가정하지 않는다. 서열 응답의 모델 선택과 해석에 대한 근거는 [Bürkner와 Vuorre의 서열 회귀 논문](https://journals.sagepub.com/doi/10.1177/2515245918823199)을 참고했다. 이 구현이 해당 논문의 회귀 모델을 사용한다는 의미는 아니다.

모델의 복잡성과 별개로 검사와 비교가 필요하다는 원칙은 [Bayesian Workflow](https://arxiv.org/abs/2011.01808)를 참고했다. 식사 그룹과 시점을 지키는 평가 분리는 [scikit-learn 공식 교차 검증 문서](https://scikit-learn.org/stable/modules/cross_validation.html)의 그룹·시계열 자료 경계를 참고한다. 실제 검사는 이 저장소의 JavaScript와 Swift로 수행한다.

### 독립 합성 비교

생산 알고리즘을 읽기 전에 [159개 가상 식사](../../scripts/tba-engine/advanced-personal-cohorts.json)를 동결하고, 그중 61건을 시점 순서대로 평가했다. 평가 대상 식사 전체는 학습에서 제외했다. 평가 시 강도·부위·시점·음식 종류는 명시적으로 제공했으므로, 이 결과는 감각 조건이 주어진 상황의 응답 비교다. 음식을 먹기 전에 감각을 알아내거나 메뉴 선택 성공을 예측한 검사가 아니다.

모델의 잘못된 판단은 0건, 기준선은 22건이었다. 이는 수작업 합성 자료의 개발 검사이며 실제 사용자 정확도가 아니다. 기준선은 같은 입력과 시간 경계를 사용한 감각별 식사 최다 응답으로, 동률이나 3회 미만이면 유보한다. 초기에 발견한 미관찰 조건의 과잉 일반화와 이후의 과도한 유보도 [독립 평가 보고서](tba-advanced-model-evaluation.md)에 남겼다.

### 계산량 점검

같은 감각의 단순 가상 관찰 1,000개를 로컬 JavaScript에서 계산하는 단발 점검은 초기 약 12,038ms에서 집계 재사용 후 약 147ms로 줄었다. 식사 하나를 제외할 때 전체를 다시 묶는 대신, 이미 계산한 식사 응답 분포에서 해당 식사의 한 표를 빼서 같은 안정성 조건을 검사한다. 이 측정은 단순 입력에 대한 개발 환경 점검이며 iPhone의 응답 시간이나 다양한 실제 기록의 성능을 보장하지 않는다.
